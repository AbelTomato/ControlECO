# 开发日志 2026-10-13


## 时间未记录 · 入账方式三开关（入账提醒 / 悬浮窗入账 / 自动入账）+ 悬浮卡「关闭即入账」（v0.5.2-beta）


### 需求

设置页原来只有一个「自动入账」开关，捕获后的处置方式表达不全。改为三个开关，语义一次说清：

- **入账提醒**：捕获到动账时发横幅通知（点通知进待确认列表处理）；也是悬浮卡弹不出时的兜底；
- **悬浮窗入账**：捕获时弹出底部确认卡——**关闭卡片（点 ✕ / 点卡片上方空白 / 长时间不操作）视为入账**，
  只有点「忽略」才不入账；
- **自动入账**：捕获到账单直接入账（保留既有 ±60s 同笔预检，不双记账）。

**互斥**：悬浮窗入账 ⇄ 自动入账（同一时刻只能选一种"免确认"方式）；入账提醒可与任一方式叠加。
三个开关在设置页「自动记账」段顶部一字排开，权限页的同名开关与它们联动（同一份状态）。

### 关键设计决策

- **关闭卡片 = 入账**（本期语义变更；原实现是「收起不丢单 + 补发通知」）：卡内当前值
  （用户可能已改过金额/商户/分类/账户）直接落账，并弹「已记入 · 撤销」细条兜底（约 6 秒可撤销）；
  点「忽略」才是明确的"不入账"。
- **金额待补录条目例外**：金额为 0 或分类/账户不全时关闭不入账，保留待确认并按「入账提醒」
  补发通知——0 元不能记成账。判定抽成纯函数 `dismissOutcome(snapshot)`（可单测）。
- **进入应用 ≠ 关闭卡片**：打开应用（或点通知进应用）时卡片只移除、不落账，条目留在待确认列表——
  避免"打开应用被动入账"；只有用户在卡片上的关闭动作才视为入账。
- **互斥落在数据层**：`setOverlayConfirmEnabled(true)` 自动关自动入账、`setAutoEntryEnabled(true)`
  自动关悬浮窗入账并收起已弹出的卡片；ViewModel 同步两个状态流，任何入口切换都不会出现"两个都开"。
- 卡片关闭回调由 `onCollapse()` 改为 `onDismiss(DismissSnapshot)`：卡内当前值随回调带回，
  窗口先移除、再回落账动作（确认/保留两条分支）。

### 验证

- 单测：**325 例 0 失败**（新增 `OverlayDismissOutcomeTest`：齐备入账 / 0 元保留 / 缺分类账户保留 / 负数保留）。
- 构建：assembleDebug / assembleRelease 通过（versionCode=26 / v0.5.2-beta）。
- 待真机验收：三个开关的互斥联动；付一笔后点 ✕ 关卡片 → 出现「已记入 · 撤销」；
  点「忽略」不入账；金额待补录条目关闭卡片后仍留在待确认列表。

### 真机验证发现并修复的三个问题

1. **卡片收起时回调被提前清空**：`dismissConfirm() → removeConfirmWindow()` 会清掉 `collapseCallback`，
   而自动收起的 Runnable 在之后才调用它 → **自动收起后不补发通知**（丢提醒）。
   修复：Runnable 先取出回调再移除窗口（`ConfirmCardWindow`）。
2. **用户点 ✕/上方空白时窗口没被移除**：`onCollapse` 只发了通知，没调 `dismissConfirm()` → 卡片悬着不走。
   修复：`onCollapse` 里先 `dismissConfirm()` 再补发通知（`CaptureCenter`）。
3. **前台匹配规则过严**：跳转支付（京东下单 → 拉起微信支付）时支付通知到达时前台是京东而不是微信，
   卡片被抑制成普通通知。修复：新增"前台应用属于监听目录（支付语境）"即允许弹卡
   （`OverlayConditions.foregroundIsPaymentContext`，纯函数判定 + 单测）。
4. 顺带修显示名：**未收录短名单的银行 App 推送**在列表/卡片里显示原始包名（`com.xxx`），
   改为退回规则名前缀（`NotificationRules.sourceLabelOrRule` + 单测）。
5. 显示润色：待确认列表的来源行在规则名已含来源前缀时不再重复
   （原为"工商银行通知 · 工商银行通知·支出"，现为"工商银行通知·支出"；微信同理）。

## 时间未记录 · 补全自动记账链路（五）：监听范围可控 + 商户归类学习（v0.4.19-beta）


### 需求

- 通道越加越多（银行推送、电商收银台），全量监听既吵又费电——用户需要按应用开关。
- 归类一直靠静态关键词（CategoryGuesser），确认过的商户下次还要再选一遍——"越用越准"是最有价值的
  产品级能力（把确认过的商户沉淀成规则，闭环到下次捕获）。

### 关键设计决策

- **监听 App 目录**（`CaptureAppCatalog` + 设置页「监听的 App」）：支付 / 银行 / 电商外卖三组，
  逐应用与整组开关；存 SharedPreferences 字符串集合、缺省读回目录默认值（首读写回，之后以用户为准）。
  **语义边界明确写进设置页**：目录只覆盖"包名可枚举"的通知/页面通道；短信与目录外未知银行 App 的
  动账推送不受目录影响（各自有号码/签名闸门）——`watchedOrUnknown` 纯判定锁死这条语义。
- **商户归类学习**（Room v7→v8 `merchant_rules`，唯一索引 `(matchKey, type)`）：
  - 学习时机：确认待确认条目（悬浮卡与列表两条路径共用 `PendingActions`）+ 编辑捕获来的交易；
    **手动记账不学习**（一次性备注会污染规则）；
  - 键归一化（`MerchantRules.keyOf`，纯函数）：去空白标点、小写、截断 20 字；
    平台通用词（微信支付/拼多多/转账…）、纯数字、过短词、含金额的通知原文一律不入库；
  - 应用优先级：**学到的规则 → 关键词猜测 → 该方向的「其他」**；账户同理；
  - **存在性校验**：应用规则前校验分类/账户仍在（分类被删后规则自动失效，不会写坏账目）；
  - 条数封顶 500（启动清理 + 每次学习后收敛）；设置页新增「商户归类」管理页（列表/单条删除/清空）。

## 时间未记录 · 补全自动记账链路（四）：无障碍收入方向 + 保活自检（并入 v0.4.18-beta）


### 需求

微信转账收款、拆红包、收款到账**只有页面没有通知**——通知通道覆盖不到，而页面通道此前只认支出方向；
另外"通道明明开着却抓不到"的两大来源是：监听假死（状态显示已连接）、应用更新后通知使用权被系统静默关闭。

### 关键设计决策

- **收入方向解析**（`PageRules.parseIncome`）与支出路径同为宁漏勿错：
  - **"对方已收钱"是付款方状态的支出页**（付款完成后显示，同时含"已收钱"）——自测曾把它当
    收入信号，这里连同"等待对方确认收款"（付款方的待收款态）一起显式排除；
  - "零钱明细"这类明细/列表页不是某笔交易的结果页，不记；
  - 与"待确认收款"（收款方状态）区分：前者排除、后者识别；
  - 付款方提取覆盖"来自张三 / 张三向你转账 / 领取了王五的红包"三种句式；
  - 红包与普通收款分开命名（`微信·红包` / `微信·收款`），待确认与溯源页据此显示。
- **失败/取消短语拒绝表**（自测整理的拒绝表）：支付失败/付款失败/交易失败/交易已取消/
  交易已关闭/订单已取消/订单已关闭/已撤销——出现即跳过（支出与收入两条路径共用）。
- **收通知即自愈**：收到任何通知都证明监听活着，直接修正连接状态，
  同时修掉"状态显示已连接但实际假死"与"实际活着而状态为假"两类误报。
- **分级重连**（0 / 1.5s / 6s，最多 3 拍）：`requestRebind` 是官方允许的软重连方式，
  不做禁用/启用组件的硬重启（那会影响其他系统服务对该应用的绑定）。
- **更新后重授权提示**：`PackageReplacedReceiver`（MY_PACKAGE_REPLACED）+ 冷启动兜底比对

- **无障碍开关双源检测**（AccessibilityManager 已启用列表 + Settings.Secure 字符串，长短组件名都比对）：

## 时间未记录 · 补全自动记账链路（三）：电商收银台 + 折叠通知金额补全 + 金额待补录/忽略（v0.4.18-beta）


### 需求

- 电商/外卖（京东/淘宝/拼多多/抖音/美团/饿了么）的付款与退款没有通道覆盖；这些应用的营销与
  物流推送极密集，直接放开包名会把捕获日志刷爆、还容易把"待支付"记成账。
- 微信折叠通知（`[N条]`）摘要常不带金额，金额只存在于子通知里；方向可辨但金额缺失的交易
  此前直接丢弃（无从补录）。

### 关键设计决策

- **电商通道比支付三包多一道确认短语硬闸门**：必须命中"已支付/支付成功/付款成功/交易成功…"才解析，
  把"待支付/待付款/订单已提交"这类未完成状态与物流/营销推送挡在外面——**包名清单只做筛选，
  正文确认短语才是闸门**（包名清单会随版本漂移，不能当安全边界）。
- **折叠补全**：摘要自身解析不出账务明细时才去 `activeNotifications` 找同组子通知；
  同包回退窗从 5 分钟级**收紧到 90 秒**且候选必须自身像账务明细——
  否则会把很久以前的无关支付通知配到当前摘要上（把旧金额记成新交易）。
- **金额待补录**：方向可辨但金额缺失 → 入队 0 元占位条 + 通知栏「输入金额」直接回复（零跳转）；
  补录后重算去重键（保留来源段/方向段/分钟桶）；同笔完整捕获到达即清掉占位条；
  **0 元条目不参与「全部确认」**，必须逐条补录或丢弃。
- **「忽略」action**：通知栏一键丢弃误报。RemoteInput 要求 PendingIntent 必须 MUTABLE
  （Android 12+ 硬要求），因此接收器额外做组件来源校验（exported=false + 显式组件双保险）。

### 实现

- `NotificationRules`：`checkoutPackages`（11 个电商/外卖包名）+ 确认短语硬闸门；
  `parseDirectionOnly` + `DirectionHint`（方向可辨金额缺失）；`looksLikeGroupedSummary` /
  `looksLikeLedgerDetail`（折叠与明细判定）；`isInterested` 扩到电商三包。
- 新增 `GroupNotificationResolver`（折叠摘要子通知补全，纯函数）+ `AmountReplyReceiver`
  （通知栏输入金额）+ `CaptureActionReceiver`（通知栏忽略）。
- `NotificationCaptureService`：文本快照纳入 `EXTRA_SUB_TEXT/EXTRA_SUMMARY_TEXT`；
  摘要无金额时用子通知的文本与时间替代（`grouped summary enriched from child`）。
- `CaptureCenter`：`handleAmountMissing` / `postAmountRequestNotification`（RemoteInput + 忽略）/
  `applyPendingAmount` / `onAmountReplied` / `supersedeAmountStubs` / `ignoreFromNotification`；
  待确认横幅统一带「忽略」action；`CaptureMerge.dedupKeyWithAmount`（换金额重算键，纯函数）。
- `Daos`：`updateAmountAndKey` / `deleteAmountStubs`；`PendingScreen`：金额待补行 + 补金额弹窗 +
  全部确认跳过提示；设置页「金额待补录」开关（默认开）；Manifest 两个新接收器。

### 验证

- 单测：**306 例 0 失败**（新增 `GroupNotificationResolverTest` 13 例、电商闸门 5 例、

## 时间未记录 · 补全自动记账链路（二）：悬浮确认卡（底部卡片·本软件风格）（v0.4.17-beta）

## 时间未记录 · 补全自动记账链路（一）：银行动账通道 + 解析加固 + 跨通道归并（v0.4.16-beta）


### 设计梳理（先写文档再动手）

- 新增 `docs/自动记账捕获机制.md`：把捕获链路的机制设计、方案取舍与自测验证记录成文
  （通道分工、多层去重、商户学习、失败/取消短语拒绝、悬浮确认卡底部卡片方案，
  见本系列后续条目）。
- 仓库内未合并分支 `feat/capture-refs-integration`（基于 10-07 旧代码的同方向草稿）**逻辑移植**，
  并修正其缺陷（"不在支付白名单里即视为银行侧"的误判会把电商渠道错误归并）；
  `docs/自动记账捕获机制.md` 同步记录明确不做的项（无障碍服务名伪装、截图 OCR、云同步）与理由。

### 需求

银行卡直接刷卡/被扣款时可能没有任何 App 通知——银行动账短信是唯一的线索；银行 App 的动账推送
同样应该被捕获；同一笔被支付通知 + 银行动账双通道捕获时不能算成两笔。另把上一轮规则加固暴露的
金额解析缺陷（千分位被截断成静默错账）一并修复。

### 关键设计决策

- **短信与银行 App 推送共用一套解析**（BankLedgerRules）：两者是同一文本形态，拆两套必然漏改一处；
  短信侧比推送多一道发送号码闸门（95588 等，含 +86 前缀），推送侧用「正文【银行名】签名 +
  包名短名单」两道线索——包名清单会漂移，只做兜底、不做闸门。
- **金额提取带上下文**：余额/可用/额度上下文出现则不取（"余额10000.00元，消费123.45元"不再取错）、
  千分位（`1,234.56` 不再截断成 `234.56`）、上限 ¥1000 万（订单号/手机号被当金额时宁漏勿错）。
- 方向判定退款优先、收支同现即放弃；银行营销短信靠两级黑名单（硬噪声一票否决；促销词仅在
  没有交易确认短语时否决，避免"已支付50.00元，享优惠"这类真实短信被连交易一起丢）。
- **跨通道归并**（CrossChannelDedup）：±130s + 金额/方向/退款全等 + **通道类别相异**（支付类⇄银行类）
  才并；未知来源不参与；同类别内（云闪付⇄银行短信）保守不并——不读卡号无法区分"同卡两通知"与
  "两卡同额"，宁可留两条由用户丢弃，也不冒把两笔真实交易并成一笔的风险。归并时银行侧只追加
  账户线索（"银行 工商银行(1234)"）到备注，金额/时间/方向一律以既有条目为准。
- **隐私最小化**：既非银行号码、正文也无银行签名的短信在采集层直接丢弃（内容不入库）；
  短信通道默认关，只收新到短信（RECEIVE_SMS：不读历史、不解码彩信、非默认短信应用、不 abortBroadcast）。
- 账户推测按银行名 + 全部别名匹配（账户名「招行卡」能对上「招商银行」）；交易来源新增 BANK，
  待确认确认/自动入账按来源写入。

  停止后系统回写 `enabled_accessibility_services`）。本次冒烟 force-stop 后本应用的无障碍采集被
  系统关闭，而 `settings put secure` 需要 WRITE_SECURE_SETTINGS——Android 12+ 起 shell 默认没有
  该权限（MIUI 上实测被拒），无法用 adb 还原，只能人工在系统设置里重新开启。
  **以后需要停进程时用 `am kill`（后台杀进程、不置 stopped 态）或在应用内退出，不要 force-stop。**
- Kotlin 字符串模板里 `$AMT元` 会被整体解析成一个标识符（CJK 是合法标识符字符）——正则插值必须写
  `${AMT}元`，否则编译报 Unresolved reference。
- 噪声黑名单会误伤真实的免密/自动扣款通知（既有真实样本"…有一笔2.98元的免密/自动扣款支付，
  点击领取6个支付宝积分。"）——把这类确认短语补进 confirmPhrases 才保住；黑名单每次扩容都要用
  既有真实样本全量回归。
