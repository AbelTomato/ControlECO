## 时间未记录 · 自动记账溯源：开发者功能「记录记账来源」（v0.4.15-beta）


### 需求

开发者功能新增「记录记账来源（溯源）」（**默认关**）：开启后，每一次与入账有关的捕获都把
**原始来源**（通知原文 / 页面文本快照）连同解析结果与处置方式留档，供日后回查"这笔账是从哪个
页面/通知来的、当时是怎么被处理的"。

### 关键设计决策

- **与捕获日志分工**：捕获日志（captured_notifications）是"写规则用"的滚动样本——7 天/2000 条、
  含未识别噪音、与账目无关联；溯源表（capture_traces）是"每笔入账的持久证据"——只按条数封顶
  1000 条、不含未识别、每行能解析到对应账目。两表互不影响，捕获日志滚动清理不会带走溯源记录。
- **状态不落库、展示时联查**：溯源只记录"当时怎么处置的"（自动入账/入队/合并回填/重复跳过/
  退款提醒），是否已入账、是否还在待确认、是否被丢弃或账单被删，一律展示时用 dedupKey 联查
  transactions（externalId = "NTF:" + dedupKey）与 pending_transactions——确认、丢弃、删账单后
  历史记录的状态自动跟随，无需任何回写，也不会出现"状态列写死了对不上"。
- **合并/重复跳过的行取"同笔条目的 dedupKey"，不取本次解析的键**：页面优先合并会改写金额，
  通知侧解析出的键从此对不上交易（externalId 用的是通知键）——只有同笔条目的键能解析到账目。
- **默认关且零写入**：关闭时连一次 INSERT 都没有（只读一次 SharedPreferences）；写入失败只记日志，
  绝不影响入账主流程——开发者功能不能成为记账链路的故障点。
- 只记"与入账有关"的捕获：未识别/未感兴趣/采集开关关闭的捕获仍只进捕获日志，溯源页不做第二份火管。

### 实现

- 数据层：Room v6→v7，新增 `capture_traces` 表（`TraceOutcome` = AUTO_ENTRY / PENDING /
  MERGED_PAGE / SKIPPED_DUPLICATE / REFUND_NOTICE），dedupKey 建普通索引（一笔可有多条来源记录）；
  迁移 SQL 与导出 schema（app/schemas/…/7.json）逐字比对一致。
- 采集层（CaptureCenter）：开关键 `capture_trace_enabled`（默认 false）；`traceCapture()` 统一入口，
  挂点七处——通知通道：自动入账、入队、重复跳过（页面侧已入账）、无金额退款提醒；
  页面通道：自动入账、入队、页面合并回填（页面快照复用 `snapshotText`，只拼一次）。
- UI：设置 → 开发者功能 → 新分区「自动记账溯源」（开关 + 「溯源记录」入口，右侧显示条数）；
  新页面「记账溯源」：折叠行 = 通道·包名·时间 / 金额·处置方式·账目状态·规则名，
  展开 = 商户·备注·去重键 + 状态说明 + **原始来源全文**（通知 title/text/bigText 或页面快照），
  行内「复制」（字段与捕获日志复制格式对齐，可直贴开发会话）与「查看账单」直达对应记录。
- 状态判定抽成纯函数 `capture/CaptureTrace.kt::traceStateOf()` 并单测：退款提醒恒为「仅提醒」；
  解析到账目 = 已入账（优先于队列残留）；无账目但在待确认队列 = 待确认；都没有 = 已丢弃。

### 验证

- `testDebugUnitTest`：**196 例 0 失败**（新增 4 例：四种处置 × 已入账/待确认/已丢弃 的映射
  与优先级、退款提醒短路）；
- `assembleRelease` 通过（versionCode=18 / versionName=0.4.15-beta）。
- **真机验证（2026-10-12，MIUI 真机覆盖安装 v0.4.14 用户数据）**：冷启动无崩溃；
  DB v6→v7 迁移成功（`user_version=7`，`capture_traces` 表与索引就位、1512 条账目完好），
  且启动清理已实际跑到新表查询（`traceDao.keepNewest`）；溯源开关/溯源页/账本入口位置
  由用户实测确认无问题。剩余观察项：开启开关后走一笔真实支付，看自动入账与待确认两条路径的
  溯源记录与「查看账单」跳转。

### 踩坑

- KSP 报 `[MissingType] Element 'CaptureTraceRow' references a type that is not present`——
  实际原因是 `@Embedded` 注解忘了 import；KSP 把无法解析的注解类型报成"引用类型不存在"，
  遇到这个错误先检查新加注解的 import 是否齐全。
- **MIUI/澎湃默认禁止 `adb shell input` 注入点击**（报 `SecurityException: ... INJECT_EVENTS`，
  需用户在开发者选项另开「USB 调试(安全设置)」）——想用 adb 脚本自动点按走查 UI 是走不通的
  （uiautomator dump 也可能因界面持续动画拿不到 idle）；本机自动化点按验证只能靠
  instrumentation（Compose UI 测试），或干脆人工点。


## 时间未记录 · 放弃灵动岛，动账提醒回归纯通知（v0.4.14-beta）


### 决策过程（用户参与）

- v0.4.13 做了悬浮窗模拟的灵动岛，真机验证发现**MIUI 把 `TYPE_APPLICATION_OVERLAY` 窗口强制排在
  状态栏下方**（`dumpsys window`：加 `FLAG_LAYOUT_IN_SCREEN` + y=0 后窗口 frame 顶部仍是 152px =
  状态栏高度），看起来只是"顶部悬浮卡"，贴不到摄像头开孔。
- 用户问为什么不用通知实现 → 结论：**安卓上"灵动岛"只能悬浮窗模拟**——iOS 灵动岛是 Live Activities
  API 而非通知；小米澎湃 OS 的「焦点通知/超级岛」虽属通知体系，但是**白名单审核制**（美团/饿了么等
  过审应用才能上岛），侧载自用应用进不了白名单（社区绕过要 Xposed，不可取）；普通通知（含横幅）
  永远渲染在状态栏下方，画不进摄像头区域。
- 用户权衡后拍板：**放弃灵动岛，只用通知**。悬浮窗方案从 v0.4.12 的旧悬浮确认窗起本来就被
  否定（UI 难用难看），不再保留任何悬浮窗代码。

### 本次改动

- 删除 `FloatingIslandWindow` 与 CaptureCenter 全部撞岛逻辑（`island_enabled` 开关、maybeShowIsland、
  4s 延迟、confirmDirect/deletePendingFor 孤儿函数、showIslandTest/scheduleIslandTest、
  ROUTE_ISLAND_TEST 调试路由、cancelCaptureNotification/appInForeground 失去调用方一并删除）。
- 悬浮窗彻底退场：Manifest 移除 `SYSTEM_ALERT_WINDOW`；CapturePermissions 去掉 OVERLAY 项
  （权限自检只剩 通知监听/无障碍/通知权限）；设置权限页删掉悬浮窗 section（页面回归两块权限），
  动账通知提醒行恢复常驻可编辑；开发者功能删掉弹窗测试入口（保留 20 秒测试通知）。
- 保活页"支付保险箱/支付保护中心"指引从"悬浮确认被拦截"改写为"页面采集被拦截"（无障碍读页仍受
  支付保护层影响）；关于页隐私说明删去悬浮窗权限表述。
- 动账提醒现状 = 单通道：捕获入队 → `announceCapture` 发横幅通知（IMPORTANCE_HIGH，确定化 id
  `pending|dedupKey`）→ 点击进待确认。退款关联提醒同为纯通知。
