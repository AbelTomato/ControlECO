- **灵动岛接管通知**（用户确认的三条产品决策）：
  1. `修改` = 卡内展开编辑（不跳 App；无焦点窗口不能弹键盘，收款方仍在 App 内改）；
  2. 接管 = 开启灵动岛期间不发动账通知，设置里通知开关**保留原值但置灰**并显示「灵动岛已接管」，
     关闭灵动岛后自动恢复；
  3. 岛弹出 30s 未处理 → **补发通知兜底**（防 MIUI 支付保护拦截/用户没看到而漏记）。
- 兜底链完整（`maybeShowIsland`，`island_enabled` 开关默认开，旧 `floating_confirm_enabled` 取值作首次默认迁移）：
  无悬浮权限 / 无分类账户可预填 / 4s 后本应用在前台 / addView 被支付保护拦截 → 立即补发通知；
  岛弹出后超时 → 补发通知。补发用确定化 id（`pending|dedupKey`），notify 同 id 幂等覆盖，
  页面富化路径重复调用无副作用；灵动岛确认/忽略仍会撤掉同笔通知，进 App（前台/点通知）即收岛。
- 实现沿用悬浮窗的窗口层约束（这部分与 UI 无关）：TYPE_APPLICATION_OVERLAY +
  NOT_FOCUSABLE|NOT_TOUCH_MODAL、经典 View（overlay 无生命周期宿主，不用 ComposeView）、
  4s 延迟避开支付页拦截窗口；系统"减少动画"开启时全部动效直切。
- 设置页：权限页「悬浮窗」section →「灵动岛」（状态行「灵动岛提醒」+ 开关「灵动岛提醒入账」+ 授权教程）；

## 时间未记录 · 下载前并行测速直连与镜像，选网络环境更好的路径（v0.4.12-beta）


### 需求与实现

- 此前 APK 下载是"直连优先、失败才切镜像"——直连**能连但很慢**时会一直卡在慢路径上
  （只有读超时 30s 才回退），镜像快也轮不到。
- 现在「立即更新」下载前先**并行测速**两条路径（`probeUrls` 双线程同时发起）：
  - 探测方式 = 范围 GET（`Range: bytes=0-65535`）实际读满前 64KB——与真实下载同路径、含重定向
    （直连会 302 到 objects.githubusercontent.com），耗时 = 建连 + 首段吞吐，
    能区分"能连但慢"与"快"；单条 5s 超时，失败记 null。
  - `orderedByProbe`（纯函数，可单测）：按耗时升序排，探测失败的排最后，平局/都失败保持原顺序
    （直连优先）；排序结果落日志（`download path order: [mirror, direct]`）。
  - 实际下载仍按序带回退：测速胜者中途失败（断流/校验不过）自动换另一条路径。
- 测速阶段对应弹窗里的转圈状态（进度未知），通常 1s 内完成，最坏 ~10s（两条都超时）。

### 验证

- `testDebugUnitTest`：**192 例 0 失败**（新增 orderedByProbe 3 例：快者先行/失败排最后/平局保序）；
- `assembleRelease` 通过（`versionCode=15 / versionName=0.4.12-beta`）。

## 时间未记录 · 确认更新后应用内下载并拉起安装（v0.4.9-beta）


### 需求与实现

1. **「立即更新」流程**：发现新版本弹窗（自动检查或手动「检查更新」触发）→ 用户确认 → 应用内下载 APK
   （直连失败自动改走镜像，弹窗内进度条，总大小未知时转圈）→ FileProvider `content://` 拉起系统安装器。
   用户唯一要做的是在系统安装确认页再点一次——不再需要手动下载 APK。
2. **「安装未知应用」授权闸**（`REQUEST_INSTALL_PACKAGES`，Android 8+ 侧载前置）：点「立即更新」时先查
   `canRequestPackageInstalls()`，未授权就跳系统授权页（`ACTION_MANAGE_UNKNOWN_APP_SOURCES` 带 `package:`），
   授权回来再点一次即走完整流程；下载完成拉起安装前再兜底查一次。
3. **下载实现**（HttpURLConnection，与检查共用直连/镜像思路）：6s 连接超时、30s 读超时；`.part` 临时文件，
   写完校验（Content-Length 一致 + ≥1MB 下限）再改名；同版本完整 APK 已存在则复用（覆盖"上次装到一半被打断"）；
   下载目录每次清理旧版本。
4. **弹窗内交互**：下载中隐藏按钮、不允许关弹窗（onDismissRequest 空操作），失败回到弹窗可重试；
   删掉「镜像下载」按钮（镜像选择内化为下载的自动回退）。
5. manifest 新增 `REQUEST_INSTALL_PACKAGES` + FileProvider（authorities `${applicationId}.fileprovider`，
   `file_paths.xml` 声明 update 目录的外部/内部两套路径）。

### 验证

- `testDebugUnitTest`：185 例 0 失败；`assembleRelease` 通过（`versionCode=12 / versionName=0.4.9-beta`）；
  `aapt2` 核对 `REQUEST_INSTALL_PACKAGES` 与 FileProvider 已打包。
- 装机走查待设备接回（USB 掉线）：从 v0.4.8 升级本版即可真实验证完整链路
  （检查 → 弹窗 → 确认 → 进度 → 系统安装确认）。

## 时间未记录 · 自动更新改用 releases 列表接口：latest 不含 prerelease（v0.4.7-beta）


### 发现

v0.4.6-beta 发布后核对 API：`releases/latest` 仍返回 404。原因——**latest 只认正式发布，不返回 prerelease**，
而本项目 beta 分发的 release 全部标了 prerelease，靠 latest 永远查不到版本。

### 修复

- 查询端点改为 `releases?per_page=5`（未认证即返回全部已发布 release，新→旧，含 prerelease；
  草稿未认证不可见，不会误取）。
- 解析改为**数组取第一个对象**：tag/资产/说明都截到第二个 `tag_name` 为止——最新 release 没挂 APK 时
  不会错配到旧版本的资产（新增单测）。
- 直连与镜像（gh-proxy.com）对带查询串的列表接口都实测可用；版本 v0.4.7-beta（versionCode 10），
  单测 185 例 0 失败，装机覆盖安装正常。
- 本次发布同时真实验证了更新链路：手机上的 v0.4.6-beta（versionCode 9）下次检查会提示升级到 v0.4.7-beta。


## 时间未记录 · 迁仓 ControlECO + 自动更新 + 两例真实样本修复（v0.4.6-beta）


### 需求与实现

1. **仓库迁移**：个人页底部 GitHub 链接与 git remote 都改为 `ArrogHie/ControlECO`（原 MyGcoin 弃用）。
2. **自动更新**（设置 → 其他 → 「自动更新」，默认开；`update/AppUpdate.kt`）：
   - 启动时后台查 `api.github.com/repos/ArrogHie/ControlECO/releases/latest`，**直连失败/超时（6s）改走镜像**
     `gh-proxy.com/` 前缀拼接（实测它代理 api.github.com；ghfast.top 不支持 API 前缀，弃用）。
     仓库还没有 release 时 API 404 → 直接静默（镜像也必然 404，不浪费时间）。
   - 版本比较用语义化解析（tag 如 `v0.4.6-beta`；数字段逐位比，同数字段时稳定版 > 预发布）；
     解析失败一律"不提醒"（宁可不弹）。
   - 发现新版本弹一次应用内对话框：「下载更新」（GitHub 直连）/「镜像下载」（gh-proxy 前缀）两个按钮 + 「下次再说」，
     下载交给系统浏览器。两次检查最小间隔 2h（进程常驻时不每次打开都打 API）。
   - 从捕获通知进入 App 时不检查（不打扰确认动线）；开关关闭时不检查。
   - **manifest 新增 INTERNET 权限**——这是应用唯一的联网用途（只读 releases 接口，不上传数据），README 已改口径。
3. **通知 bug：免密扣款 2.98 元被抓成 6 元**（真实样本：你在浙江嗨便利网络科技有限公司有一笔2.98元的免密/自动扣款支付，点击领取6个支付宝积分。）：
   - 失败链路：反向正则「金额+元+最多3个字+关键词」跨不过「的免密/自动」6 个字 → 落回正向正则 →
     「扣款」后 7 个字处正是营销文案的「领取**6**个支付宝积分」，把 6 当成金额。
   - 修复（两手）：反向窗口 `{0,3}` → `{0,8}`（标点仍是硬边界，"支出，领1元红包"不会跨）；正向金额**必须带"元"收尾**
     （¥ 前缀的走原有 ¥ 兜底）——营销裸数字从此进不了正向正则。
4. **页面 bug：支付页商户"杭州深度求索"没被抓到**（真实样本：支付成功￥5.00 | 杭州深度求索 | ￥5.00 | 付款方式 | …）：
   - 先复现：把样本写成 `PageRulesTest` 用例，**当前引擎解析是正确的**（无标签商户锚点兜底命中）——问题在引擎之后：
     - **待确认列表与确认弹窗根本不显示商户**：页面捕获的 counterparty 只进了数据库，用户在确认动线里全程看不到、
       也没法核对修改，观感就是"没捕获到"。修复：待确认行显示「收款方 …」，确认弹窗加可编辑的「收款方/商户」输入框
       （预填捕获值，`confirmPending` 支持传入改后的值）。
     - **半渲染快照会抓错**：页面分阶段渲染，商户节点未就绪的快照走兜底提取时会把导航节点「回首页」当收款方
       （「返回商家」因含"返回"早被排除，「回首页」没有）。修复：`fallbackExcluded` 补「首页/客服/更多」；
       补一条半渲染快照单测（此时收款方应为空而不是错的）。
5. **文档**：维护指南的正/反向正则描述同步（正向要求"元"、反向 3→8 字）；README 补自动更新与联网口径。

### 验证

- `testDebugUnitTest`：**184 例 0 失败**（新增：通知免密扣款样本 1、页面真实样本 + 半渲染快照 2、AppUpdate 纯函数 9）。
- `assembleRelease` 通过；`aapt2 dump badging`：`package com.controleco.app versionCode=9 versionName=0.4.6-beta`。
