# 自动记账捕获机制（设计说明）

> 本文档记录我ECO自动记账链路的机制设计、方案取舍与实测依据，与实现同步维护。
> 实现细节与验证记录见开发日志同日系列条目；通道状态见开发方案 §9。
> 版本：2026-10-13。

## 一、机制速览

捕获链路是「系统通知监听 + 无障碍页面采集 + 银行动账短信」三通道合一，每条通道走同一条
下游：原始快照落库（不解析）→ 规则引擎解析 → 待确认队列 / 自动入账 / 悬浮确认卡。

| 维度 | 本项目的选择 |
|---|---|
| 采集主力 | 系统通知监听（微信/支付宝/云闪付/银行 App 推送）+ 无障碍页面采集（补全商户、支付方式）+ 银行动账短信（无任何 App 通知时的唯一线索） |
| 应用覆盖 | 30 个应用的目录（支付/银行/电商三组），逐应用可开关；解析统一走规则引擎（确认短语 + 金额提取），不为单个应用写死解析器 |
| 入账方式 | 捕获**先直接入账**（三种方式任一开启即入账）；悬浮窗入账在此基础上弹卡：改完关掉卡片即同步修改、点「忽略」删除这笔；入账提醒发「已记入一笔账」通知；自动入账不打扰；三个全关才退回待确认队列 |
| 确认前防错 | 三层去重：内存 10s 重发窗口 → 合并池 10s 同源合并（页面信息优先）→ 自动入账前 ±60s 同笔数据库预检；入账再以 dedupKey 唯一索引兜底 |
| 归类学习 | 确认/保存时按商户名回写规则（下次自动预填分类/账户），条目封顶 500 条 |
| OCR | 不做（本地优先、轻量约束；当前无真机样张可调规则） |
| 保活 | 通知监听自愈（收通知即自愈 + 分级重连）+ 更新后重授权提示 + 分品牌保活页引导 |

## 二、悬浮确认卡（底部卡片）的设计取舍

**结论：卡片放屏幕底部。** v0.4.13 灵动岛方案（顶部 placement）失败的原因正是顶部放置——
MIUI 把 `TYPE_APPLICATION_OVERLAY` 强制排在状态栏下方，窗口被压扁不可用；底部卡片天然绕开。

窗口与交互（与 `ConfirmCardWindow.kt` / `ConfirmCardContent.kt` 对应）：

1. **全屏透明窗口 + 底部卡片**：`MATCH_PARENT`、`TYPE_APPLICATION_OVERLAY`、
   `NOT_TOUCH_MODAL｜LAYOUT_IN_SCREEN｜LAYOUT_INSET_DECOR｜WATCH_OUTSIDE_TOUCH`、
   RGBA_8888、cutout=shortEdges；点卡片上方空白 = 关闭卡片（不穿透、不丢弃交互）。
2. **先入账、后确认**：卡片打开时这笔账已经记好——点 ✕、点卡片上方空白、长时间不操作（60 秒）
   都保留这笔，并把卡内改过的字段同步回账目（「已记入 · 撤销」细条可一键撤销整笔）；
   点「忽略」才删除这笔。卡片弹不出来（无权限/被拦截/时机不巧）时账也不会丢，这正是先入账的意义。
3. **金额待补录条目例外**：金额缺失的条目无法入账，留在待确认队列并按「入账提醒」补发通知
   （判定见 `dismissOutcome()` / `canSyncOverlayEdits()` 纯函数与单测）。
4. **`addView` 失败即回落通知**：无权限/被支付保护层拦截时 `showConfirm` 返回 false，
   调用方回落横幅通知；「Toast 可见而卡片不可见 = 被支付保护层拦截」是排查判别法。
5. **卡片/通知互斥**：卡片展示某笔时抑制该笔的横幅通知，避免同一笔打扰两次。
6. **一窗口两状态**：确认后卡片退场、换成「已记入 … · 撤销」细条（同一套窗口参数）。

真机实测（MIUI / Android 16）：窗口显示、Compose 在 overlay 内的生命周期接入、卡内输入框
键盘、暗色跟随均验证通过；样例卡与开发者调试入口（立即/延迟 20 秒）保留在开发者功能里。

**不做**：顶部 placement（MIUI 压缩，v0.4.13 已有失败记录）、拖拽/缩放窗口、前台服务常驻兜底
（用通知兜底，更轻）。

## 三、通道清单与执行状态

| 能力 | 状态 | 说明 |
|---|---|---|
| 通知监听通道 | ✅ | 微信/支付宝/云闪付 + 电商收银台确认短语 + 银行 App 推送（正文签名闸门） |
| 短信通道 | ✅ | 只收新短信（RECEIVE_SMS，不读历史、非默认短信应用）；号码 + 银行签名双闸门 |
| 无障碍页面采集 | ✅ | 支出 + 收入（转账收款/红包）双方向；失败/取消短语拒绝表 |
| 跨通道归并 | ✅ | 支付类 ⇄ 银行类 ±130s、金额/方向/退款全等才归并；同类别通道保守不并 |
| 金额提取加固 | ✅ | 千分位、余额上下文排除、卡尾号遮罩、上限 1e9 分 |
| 悬浮确认卡 | ✅ | 先入账后弹卡：改完关掉即同步、忽略删除；未授权/被拦截时账已记好，回落「已记入」通知 |
| 商户归类学习 | ✅ | 确认时学习，Room v8；优先级：学习规则 → 关键词猜测 → 其他 |
| 监听范围可配 | ✅ | 「监听的 App」逐应用开关（支付/银行/电商三组） |
| 截图 OCR | ⬜ 不做 | 无真机样张、重引擎，与轻量约束冲突（理由见第四节） |

## 四、明确不做的（附理由）

- **无障碍服务名伪装 / 声明为无障碍工具**：靠伪装成系统组件规避系统提示与用户感知，
  属欺骗性设计，不做；服务名与描述如实写明用途。
- **截图 + OCR**：本地 OCR 引擎（模型 + 运行时约 30MB 量级）与"本地优先、轻量、可维护"
  冲突；且当前无真机样张可调规则。等有明确需求再评估。
- **服务端 AI 归类 / 云同步 / 云规则**：本项目本地优先，架构上不引入。
- **5 秒自动确认倒计时、拖拽缩放卡片**：收益低、误操作风险高，不做。
- **邮箱中转、Excel 模板生成等导入玩法**：与本轮"捕获链路"无关。

## 五、本地账本备份与恢复

- 在「账单导入」页面的「本地账本备份」区，点击「导出备份」并通过系统文件选择器选择保存位置，可导出格式版本为 1 的 JSON 文件 `controleco-ledger-backup-v1.json`。文件包含账户、分类、交易、商户学习规则及分类引用的自定义图片；不包含待确认条目、捕获记录、设置偏好或分类月预算。
- 恢复时在同一区域点击「恢复备份」并选择 JSON 文件。应用校验格式后先显示备份时间和记录数量；用户确认后才整体替换当前账户、分类、交易和商户学习规则，不执行合并。无效文件或恢复失败时不会把部分账本写入数据库。
- 该备份包含财务隐私。建议导出后将 JSON 复制到手机以外的安全位置，并限制文件访问；恢复时由系统文件选择器授权访问，不需要应用申请广泛存储权限。文件可用于卸载重装、换机或更换应用签名后的账本恢复，但不能恢复上述排除的数据。
- 恢复不改变 Room schema，也不触及捕获/溯源记录和设置数据。未来格式变化须使用新的格式版本；不支持的版本会被拒绝。

## 六、遗留与待验收（诚实记录）

- 银行短信/银行推送**没有真实样本**（仓库内只有微信/支付宝日志），规则按通用形态推演 + 合成单测，
  首条真实样本到手后按 `logcat -s ControlECO` 与捕获日志扩规则（见维护指南）。
- 电商收银台、微信收入页（转账收款/红包）格式未经真机验证，靠"确认短语硬闸门 + 方向互斥"保证
  宁漏勿错；均可在设置里逐项关闭。
- 云闪付通知与银行短信这两种通道当前**不互相归并**（无法在不读卡号的情况下区分
  "同卡两通知"与"两卡同额"），宁可留两条待确认由用户丢弃，不冒并错的风险。
