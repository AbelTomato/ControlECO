## 2026-10-05 · 防杀后台与自启动设置（保活引导页）

### 实现

- **品牌识别**：`Brand.from(厂商字符串)` 纯函数映射（小米/红米/POCO、华为、荣耀、OPPO、一加、真我、vivo/iQOO、三星、其他）；荣耀先于华为判断，老荣耀机型（厂商字段报 HUAWEI）走华为指引，两者步骤基本一致。
- **分品牌保活清单**（依据前期梳理：华为官方启动管理三开关、小米省电策略无限制与十秒盾、OPPO 应用速冻/睡眠待机、vivo i管家等）：每步含标题、操作路径说明、可选跳转按钮（自启动页 / 应用信息页）。
- **跳转工具**：自启动页按品牌维护已知安全中心组件候选列表逐个尝试（华为 systemmanager 启动管理、小米安全中心自启动、OPPO coloros/oppo/oplus、vivo permissionmanager/iqoo、荣耀 hihonor），全部失败回退到本应用"应用信息"页并 Toast 提示手动查找。
- **电池优化白名单**：可程序检测（PowerManager），未忽略时提供"申请忽略"按钮（系统确认框，需 REQUEST_IGNORE_BATTERY_OPTIMIZATIONS 权限）。
- **保活引导页**：服务状态（通知监听授权/连接、最近捕获时间，带品牌机型）+ 电池优化卡 + 品牌步骤清单 + 通用排查说明（开关正常但无事件：重启→开应用→查捕获日志→重开通知使用权）；从系统设置返回时自动刷新可检测状态（Lifecycle ON_RESUME 计数触发重算）。
- 入口：设置 → 自动记账 → "防杀后台与自启动（保活设置）"。版本号 v0.2.1。

### 踩坑

- Android 11+ 显式跳转其他应用的组件必须先声明包可见性（`<queries>` 逐包声明各品牌安全中心包名），否则 ActivityNotFoundException，跳转全部静默失败。
- `Brand.from` 定义在 Brand 的伴生对象上而非 DeviceBrands 上，测试引用写错位置报 Unresolved（命名上 DeviceBrands 太像门面，改进空间：把 from 挪到 DeviceBrands 或改名）。

### 设计取舍

- 自启动、省电策略、锁后台等开关**无法程序读取**（厂商不开放接口），所以引导页定位是"能查的显示状态 + 不能查的给路径和直达按钮"，不做虚假的状态勾选。
- 申请忽略电池优化的系统弹窗在部分 ROM 可能被拦截或无效果，页面文案已说明"品牌省电策略仍需手动设置"。

## 2026-10-05 · 阶段二：通知监听采集通道（捕获→解析→待确认→入账）

### 实现

- **数据层**：Room v2→v3，新增 `captured_notifications`（原始捕获日志：采集层立即落库的原文快照，不解析，7 天/2000 条自动清理）与 `pending_transactions`（待确认队列，dedupKey 唯一索引）；开启 Room schema 导出（app/schemas/）用于逐字校验迁移 SQL。
- **采集层**：
  - `NotificationCaptureService`（通知使用权）：提取 title/text/bigText/消息样式原文交给 CaptureCenter；断连自动 requestRebind；
  - `CaptureCenter`：重发去重（同内容 10 秒窗口，防通知更新导致的重复回调）→ 原始快照落库 → 感兴趣包名走规则引擎 → 待确认入队；

- **入账链路**：确认 → 交易落库（externalId = "NTF:" + dedupKey，复用交易表唯一索引防重）；"全部确认"按默认分类（其他）+ 推测账户（微信→微信零钱、支付宝→支付宝、云闪付→银行卡）批量入账。

- 当前 compileSdk 35 的 `NotificationListenerService.onListenerDisconnected()` 是**无参**方法（老资料里带 reason 参数的签名已不存在）。

## 2026-10-05 · 退款记录显示开关（"显示退款记录"）

### 需求

默认不显示退款（与原行为一致）；设置中开启"显示退款记录"后：退回的金额标记「退款收入」、被全额退款的支出标记「已退款」，计入总收支并额外显示「已取消收支」合计；关闭则不显示、不计入。

### 关键设计决策

- **退款记录始终入库、开关只控制显示与统计**（而不是解析时决定是否入库）：切换开关立即对全部历史导入生效，无需重新导入账单。数据库中多存的数据只是带标记的正常交易记录。
- **无需合成记录**：真实账单中微信退款本来就是成对的两行——退款到账行（收/支=收入、交易类型"XXX-退款"、状态"已全额退款"/"已退款(¥8.54)"）+ 原支出行；支付宝为"交易关闭"支出行 + "退款成功"不计收支行。解析时打标记即可。
- **部分退款的支出不打"已退款"标记**：微信原支出行状态"已退款(¥8.54)"（兼容"已退款¥8.54"）时保持普通支出（净支出本来就该是全额），退款额由独立收入行承载；支付宝部分退款原行状态仍"交易成功"，同理。
- **「已取消收支」= 退款到账金额合计**（收入侧）：全额退款时与已退款支出合计一致；部分退款时即为实际退回金额。
- 微信账单里"对方名-退款"是交易类型列的特征，交易对方列是干净商户名，分类猜测不受影响。

### 实现

- 数据层：`RefundMark` 枚举（NONE/REFUNDED_EXPENSE/REFUND_INCOME）新增到交易表；数据库 v1→v2 迁移（ALTER TABLE 加列，保留用户已导入数据）；所有月度查询（流水/收支汇总/分类占比/账户余额）加 `includeRefunds` 参数，余额查询把过滤条件放进 LEFT JOIN 的 ON 子句避免丢掉无交易账户；新增退款合计查询。
- 设置存储：SharedPreferences（"显示退款记录"布尔值），ViewModel 持有状态流，各查询流用 combine 联动开关。
- UI：设置页开关（含说明文案）；流水/统计页汇总行开启时显示第 4 列「已取消」；流水列表与导入预览的退款行显示「退款收入」/「已退款」角标；导入预览显示"退款相关 N 条"及当前开关状态提示。
- 「已取消收支」列不受开关外的其他过滤影响，仅由开关决定是否展示。

### 真实文件验证

- 微信 xlsx：**190 条全部入库**（原 157 条有效 + 33 条退款相关），中性交易仍跳过 2 条；dump 可见成对记录（姜胖胖：退款收入 50 元与原支出 50 元，时间一前一后）。
- 支付宝 CSV：**458 条入库**（444 普通 + 7 交易关闭 + 7 退款收入）+ 3 条不计收支跳过 = 官方总数 461 笔；Steam 两笔退款收入（34.80/24.48）正确识别。
- 25 个单元测试全部通过（更新微信旧版/新版 xlsx、支付宝 2026 用例覆盖全额/部分退款标记）。

### 踩坑

- 带过滤条件的 LEFT JOIN 若把条件放 WHERE，无交易的账户会因 NULL 比较被整体过滤掉，必须放在 ON 子句。
- 旧数据升级：Room 迁移列必须带 NOT NULL DEFAULT，且枚举列以字符串形式存储（Room 默认按枚举名转换）。

## 2026-10-05 · 适配 2026 版微信/支付宝真实账单格式（用户提供 docs/book 实测文件）

### 发现（真实导出与假设差异很大）

- **微信："用于个人对账"导出已从 CSV 改为 xlsx**：
  - 交易时间是 Excel 日期序列号（如 46299.627337962964），换算 = (序列号 − 25569) 天 + 小数部分×86400 秒；文件注明为 UTC+8 墙上时间，按本地时区转毫秒，与 CSV 路径语义一致；
  - 金额是无 ¥ 前缀的纯数字单元格；"不计收支"改称**"中性交易"**；
  - 表头列名不变，表头前同样有说明行。
- **支付宝 2026 版 CSV 表头大改**：
  - 列为：交易时间,交易分类,交易对方,对方账号,商品说明,收/支,金额,收/付款方式,交易状态,交易订单号,商家订单号,备注（旧版的 交易创建时间/付款时间/金额（元）/交易号 已不存在）；
  - 新增**"交易分类"列**（餐饮美食/日用百货/文化休闲…），可直接映射应用分类；
  - 交易订单号/商家订单号单元格带**尾部制表符**（trim 掉）；
  - 存在"交易关闭"的支出行，与其后"退款成功"的不计收支行成对出现，两者都跳过才不会重复；
  - 一笔可用组合支付方式（"中国银行储蓄卡(8920)&大牌补贴立减"）。

### 修改

- 新增 `XlsxReader`：正则解析 xlsx 的 sharedStrings 与第一个工作表（零依赖、可在 JVM 单测运行），支持共享字符串/内联字符串/数值单元格、缺失单元格补空、AA 以后的列号、XML 实体反转义。
- `BillParsers.parse` 按 zip 魔数(PK)嗅探 xlsx 与 CSV；`parseWechat` 时间兼容序列号；`parseAlipay` 按新表头重写、旧表头自动兼容（付款时间优先于创建时间仍保留）。
- `CategoryGuesser` 新增 `fromAlipayCategory`（官方交易分类→应用分类），未命中回退关键词猜测；餐饮关键词补充瑞幸/coffee。
- 跳过规则明确化：微信"含退款字样状态"跳过；支付宝"非成功/已到账状态"（如交易关闭）跳过；两者均只保留收/支=收入|支出的行。
- 界面文案更新导出格式说明（微信 xlsx / 支付宝 CSV）。
- 新增 `RealFileParseCheck` 手动核对工具：格式再变时把新导出文件放 docs/book，跑 `--tests "*RealFileParseCheck*"` 打印解析结果人工比对。

### 真实文件验证（docs/book；目录已 gitignore，含个人隐私禁止入库）

- 微信 xlsx：官方汇总"收入40+支出150+中性2=192 笔"，解析 **157 条有效**（190 条收支 − 33 条已退款）+ 跳过 2 条中性交易——完全吻合；金额/序列号时间/分类抽检正确。
- 支付宝 CSV：官方汇总"收入0+支出451+不计收支10=461 笔"，解析 **444 条有效**（451 − 7 条交易关闭）+ 跳过 10 条不计收支——吻合。

### 测试

25 个单元测试全部通过（新增：微信 xlsx 端到端、xlsx 读取器 4 项、支付宝 2026 新格式、旧格式保留兼容）。

### 踩坑

- 测试内构造 xlsx 夹具时，字符串单元格必须先放进 sharedStrings 表再引用下标，漏放的（交易单号、商户单号）经 shared.indexOf 返回 -1 后变成空单元格，表现为"交易单号为 null"。
- Gradle 单测的默认工作目录是模块目录（app/）而非项目根，读项目内文件要写 `../` 相对路径。

### 决策记录

- **金额一律用"分"（Long）存储**，避免浮点误差；`Money` 工具类统一解析与展示。
- **CSV 编码识别**：先 UTF-8 严格解码，失败回退 GBK；另外加了"含『交易』关键词"校验——GBK 字节序列偶发能被 UTF-8 解码成乱码而不报错，仅靠异常判断不可靠。
- **解析器用列名映射而非固定列位**：微信/支付宝改版调整列顺序时不至于直接失效。
- **退款行跳过**：微信"已全额退款"状态行、支付宝未完成（如等待付款）行不导入，避免净额重复；跳过数量在预览页明示。
- **UI 全部用 Material 3 默认样式**，按约定阶段一不做视觉打磨。
- **ViewModel 全局一个**（LedgerViewModel）：月份切换是流水/统计共享状态，且数据量级小，简单优先；后续阶段按需拆分。

### 踩坑

- Git Bash 下把 `D:/Java/...` 风格路径放进 PATH 会导致 java 找不到，需用 `/d/Java/...` POSIX 风格；而给 .bat 用的 JAVA_HOME 又必须 Windows 风格——两者混用要小心。
- `D:\AndroidSDK` 里 cmdline-tools 直接解压在根目录（非标准的 `cmdline-tools/latest` 布局），调用 sdkmanager 时显式传 `--sdk_root` 解决。

### 构建结果

- `:app:assembleDebug` 成功，产物 `app/build/outputs/apk/debug/app-debug.apk`（约 10MB）。
- `:app:testDebugUnitTest` 19 个测试全部通过。

### 踩坑（编译期）

- `stickyHeader` 自 foundation 1.7 起是 `LazyListScope` 接口的成员函数，不能（也不需要）import，写 import 反而报 Unresolved reference。
- Kotlin 不允许 `continue` 出现在 `run { }` 这类内联 lambda 中（实验特性默认关闭），"解析失败就 continue"要写成显式的 `if (x == null) { ...; continue }`。
- Material 3 的 `@OptIn(ExperimentalMaterial3Api::class)` 别忘了 import 注解类本身，报错形式是"Unresolved reference 'ExperimentalMaterial3Api'"。
- `AppLog` 直接调 `android.util.Log`，JVM 单元测试里会抛 "not mocked"，需在 `app/build.gradle.kts` 加 `testOptions { unitTests.isReturnDefaultValues = true }`。

### 踩坑（测试期）

- 金额解析最初无条件删逗号，`"1,2.3"` 会被拼成 `"12.3"` 误判有效；改为仅当整体符合千分位格式（`1,234.56`）时才移除逗号。
- AGP 首次构建报 "Failed to find target android-35"，但平台目录与 package.xml 完好，未做任何改动重跑即恢复（疑似首次配置解析时序问题）；若复现，先清理 `.gradle` 再查。
