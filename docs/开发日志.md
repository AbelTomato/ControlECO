## 2026-10-06 · 放弃微信页面捕获 + 退款关联流程 + 通知式入账提醒 + 延迟测试按钮

### 决策：微信页面通道关停

微信 a11y 事件能到达但窗口内容持续读不到（collect empty），放弃页面捕获——微信的记账由通知通道承担（实测通知识别已全部正确）。a11y 配置只留支付宝。

### 新功能一：无金额退款 → 退款关联流程

**问题**：微信折叠通知 `title=微信支付 text=退款到账通知` 没有金额，无法自动入账（带金额的退款正常入队不受影响）。
**方案**（设置开关「退款到账关联提醒」，默认开）：
- `NotificationRules.isAmountlessRefundNotice` 识别无金额退款通知 → `handleRefundNotice`：捕获日志标记「退款·待关联」+ 弹**退款关联悬浮卡**（有悬浮权限时）+ 发**系统通知**，点击均跳转「选择被退款的账单」页。
- 新页面 `RefundLinkScreen`（路由 refundLink）：列近 60 天未退款支出（`recentUnrefundedExpenses`，refundMark=NONE 过滤），点选后弹对话框：**退款金额可改（支持部分退款）**，确认后生成退款收入（REFUND_INCOME，入原账户、金额=用户输入）并把原支出标记 REFUNDED_EXPENSE——与账单导入口径一致，受"显示退款记录"开关控制。
- MainActivity 改 singleTask + EXTRA_ROUTE + onNewIntent：悬浮卡/通知点击导航到指定页（自增序号保证同路由重复点击也能触发）。

### 新功能二：动账通知提醒（悬浮窗被拦截时的可靠替代）

- 系统通知（渠道"自动记账提醒"，IMPORTANCE_DEFAULT）：待确认入队时（通知通道+页面通道）发「捕获到一笔支出/退款 ¥X · 点击确认入账」，点击进待确认队列。
- `POST_NOTIFICATIONS`（安卓 13+ 运行时）：设置页「动账通知提醒」行内"申请权限"按钮（rememberLauncherForActivityResult）；未授权时静默跳过并发日志。
- 设置开关「动账通知提醒」默认开。

### 新功能三：debug 延迟测试按钮

- 「20秒后弹窗」：按下后 20 秒弹样例悬浮窗——按下后立刻切到支付宝付款页等待，用于区分"支付页被拦截"（现在能弹的界面弹、支付页不弹）与"悬浮窗层故障"。
- 「20秒后测通知」：20 秒后发样例捕获通知，验证通知通道与点击跳转。

### 悬浮窗在支付宝支付成功页不弹的排查结论路径

手动测试弹窗能弹（窗口层 OK）→ 权限 OK；自动链路日志曾显示"未授权"（当时确实没授，后补授的）→ 现在自动仍不弹 + 延迟测试在支付页上也不弹 → **支付宝支付页上层的系统级拦截**（MIUI 支付保险箱/厂商安全层），App 层无解，通知通道是正式替代方案。

## 2026-10-06 · 微信 collect empty 定性（窗口切换过渡期）+ 空读重试

### 用户补充日志澄清：微信事件其实能到达

`a11y event pkg=com.tencent.mm type=0x800` + `collect empty pkg=com.tencent.mm`——事件到了，但 400ms 后采集时窗口内容还没就绪（18:00:22 是切进微信的瞬间，冷启动/过渡期控件树未渲染）。这推翻了此前"微信事件被系统拦截"的猜测，也说明"应用双开"假设不成立。

### 修复：空读限次重试 + 详情日志

- 空读后重试最多 2 次（每次仍走 400ms 防抖），新事件到来时计数归零——过渡期（约 1 秒级）内的后续采集通常就能读到内容。
- `collect empty` 日志带详情：`activeRoot=`（活动窗口属于哪个包）、`appWindows=`（枚举到的应用窗口数）、`readable=`（root 非空的窗口数）。下次日志可直接区分三种情况：readable>0 仍空=窗口内容真不可读（安全窗口）；appWindows=0=枚举不到本包窗口；activeRoot 是别的包=过渡期未完成。
- 规则口径按用户意见保持严格：支付页格式固定，宁可少抓不可抓错（收银台守卫、实付≤0 跳过、键值分隔符硬要求、跳过其他标签的值节点均已就位）。

## 2026-10-06 · 真机日志分析（1.log）：微信事件被拦 + 支付宝三处误提取 + 授权教程

### 日志揭示的事实（test/log/1.log，小米设备）

1. **微信无障碍事件完全没到达**：整份日志（含支付时刻前后）零条 `a11y event pkg=com.tencent.mm`，而支付宝事件正常——同服务同配置，是微信侧被系统/微信自己拦。用户引用的 `[Ntf] onPosted...已支付¥2.79` 是**通知通道**，且工作正常（下一行已 `queued pending ¥2.79`）。待查：翻聊天是否产生 event；该笔是否微信 App 内支付（免密代扣无页面）；微信是否"应用双开"（双开跑在独立用户空间，无障碍收不到事件，通知却能收到）。
2. **支付宝收银台页险些入队**：收银台含"支付成功得公交地铁1.5元多次券"营销文案 → 命中"支付成功"关键词；金额标签"支付金额0.00元"被 `amountCents<=0` 守卫拦下（侥幸）。新增**收银台守卫**：含"确认付款/使用密码/请验证"直接跳过。
3. **¥0.00 全额优惠支付错入队 ¥0.01**：成功页 `[支付成功￥0.00 | 陈自有 | ￥0.01 | 支付遇财神 | -￥0.01 | …]`——原金额策略"独立¥节点优先"抓到了订单金额￥0.01，而实付是标题节点里的￥0.00。改金额优先级：**锚点节点实付金额优先**（跳过前缀 -/减/惠 的优惠金额）→ 金额标签 → 独立节点 → 任意 ¥；实付 ≤0 直接跳过（0元支付无需记账）。
4. **"对账"被当成收款方**：`点击给商家对账` 里嵌着标签"商家"，同行值提取没要求分隔符，把"对账"当成了值；兜底扫描又把"付款方式"的值"零钱"当商户。修复：**同行值必须紧跟冒号/空格分隔符**；兜底扫描跳过"上一节点是标签"的值节点。
5. **悬浮窗"未授权"跳过是真实的**：18:00:06 那笔支付时权限确实没授，用户手动测试成功发生在授权之后。`canDrawOverlays` 是实时读取，无进程内缓存问题；被跳过的那笔不补弹，下一次支付即恢复。

### 代码改动

- `PageRules`：收银台守卫（确认付款/使用密码/请验证）；锚点实付金额优先 + 优惠金额排除（paidAmountInAnchor）；valueAfterLabel 分隔符硬要求；guessCounterparty 跳过其他标签的值节点。
- `SettingsScreen`：无障碍/悬浮窗两处加**分品牌授权教程**（可展开；品牌路径由 Brand.current() 生成；含受限设置、十秒盾、测试弹窗验证、支付保护拦截排查指引）。

## 2026-10-06 · 诊断链路升级 INFO 日志（华为隐藏 DEBUG 日志）+ 自动弹窗分支可见化

### 用户反馈：logcat 完全无输出；微信页面仍未捕获；支付宝页面正常但自动悬浮窗仍不弹；手动测试弹窗正常

**logcat 无输出的原因（重大环境坑）**：华为/EMUI 默认隐藏 DEBUG/VERBOSE 级日志，而此前链路里的关键诊断日志（`a11y event`/`snapshot`/弹窗跳过原因）几乎全用 `AppLog.d`（Log.d）——用户在真机上什么也看不到。两层解决：
1. **解锁华为 AP 日志**（可选，看全量 DEBUG）：拨号盘输入 `*#*#2846579#*#*` → ProjectMenu → 后台设置 → LOG 设置 → 勾选 AP 日志，重启生效。
2. **整条诊断链升级 INFO 级**（`AppLog.i`，华为默认可见）：`a11y event`（2s 节流）、`page snapshot`（仅支付类页面，聊天噪音不打）、`collect empty`、`page not matched`、`skip enqueue（开关关闭）`、悬浮窗全部跳过原因；DEBUG 级只留高频噪声行（指纹跳过、全量快照）。

**"手动弹窗可行、自动不弹"的分支定位**：手动测试与自动链路在 `FloatingConfirmWindow.show` 内部完全一致（同 appContext、同 post 到主线程），差异只能在弹窗调用**之前**的分支或**系统对支付页上层的拦截**。本轮把所有分支原因都打出来：
- 新增 debug 判别器：自动弹窗尝试后同步弹系统 Toast「自动悬浮窗已尝试弹出（debug）」——**Toast 是系统级窗口不受支付保护拦截，Toast 可见而悬浮窗不可见 = 被拦截的铁证**。
- 修一个静默陷阱：设置页「自动记录支付页面」开关关闭 + 调试全量开启时，页面快照照常入库（看起来"捕获正常"）但**既不入队也不弹窗且无任何日志**——现在会打 `skip enqueue（开关关闭）`，且捕获日志行显示规则名但无"已入待确认"标记。开关检查前移到富化/入队之前（此前关闭时还会错误地富化既有条目）。

### 两条链路的检查点（供真机对照）

捕获链：`a11y event pkg=…`（事件到达）→ `page snapshot texts=[…]`（读出页面文本）→ `page not matched` / `queued pending` / `enriched pending` / `skip enqueue`。微信没捕获：先看浏览聊天时有没有 `a11y event pkg=com.tencent.mm`——没有 = 事件被系统拦（支付保护中心/服务需重开）；有而无 snapshot = 窗口读不出；有 snapshot 而无 queue = 规则问题（发快照）。
弹窗链：`page snapshot` → `floating confirm skipped（原因）` → `floating confirm shown`。有 shown 无窗口 + debug Toast 可见 = 系统拦截。

## 2026-10-06 · 悬浮窗不弹的根因修复 + 捕获日志分通道 + USB 调试指南

### 用户反馈：支付页面出现但悬浮确认窗没有弹出

## 2026-10-06 · 阶段三：无障碍页面采集 + 悬浮确认窗 + 权限引导补全

### 实现内容（对照交接文档四项目标）

1. **无障碍服务骨架**：`AccBookAccessibilityService` + `res/xml/accessibility_service_config.xml`。事件只订阅 `TYPE_WINDOW_STATE_CHANGED|TYPE_WINDOW_CONTENT_CHANGED`、包名限定微信/支付宝、只读窗口内容、不申请手势能力（最小权限）。服务连接状态经 `CaptureCenter.a11yConnected` 状态流暴露给设置页/保活页；`isEnabled()` 读 `Settings.Secure.ENABLED_ACCESSIBILITY_SERVICES` 检测（保活页与设置页的"去开启"跳 `ACTION_ACCESSIBILITY_SETTINGS`）。
2. **页面识别规则**（`PageRules.kt`，风格对齐 NotificationRules，纯函数可单测）：输入=包名+页面文本快照（text/contentDescription 按控件树顺序，不依赖 viewId）。识别「支付成功页」（支付成功/付款成功/支付完成）与「账单详情页」（账单详情/交易详情），提取金额（标签行→独立 ¥ 节点→任意 ¥ 三层）、收款方/商家、支付方式、交易时间。
3. **悬浮确认窗**（`FloatingConfirmWindow.kt`）：`TYPE_APPLICATION_OVERLAY` + `NOT_FOCUSABLE|NOT_TOUCH_MODAL`；经典 View 实现（Compose 在 overlay 窗口需手工接 LifecycleOwner，不值得）；分类/账户用 ‹ › 循环选择（Spinner 弹层在无焦点窗口不可用）；确认直接入账并清同笔待确认；90 秒自动消失；忽略=删除同笔待确认条目。`SYSTEM_ALERT_WINDOW` 权限，设置页引导跳 `ACTION_MANAGE_OVERLAY_PERMISSION`。
4. **权限引导补全**：设置页加无障碍采集状态卡+开关、悬浮确认窗授权卡+开关；保活页加无障碍状态行 + **安卓 13+ 侧载"允许受限制的设置"通用第一步卡**（红色标题置顶）；分品牌补支付保护拦截对策（小米支付保险箱、荣耀支付保护中心、OPPO 系支付保护，华为已有）。

### 关键设计决策

- **跨通道去重改为 ±1 分钟容错**（`findRelatedPending`）：通知 postTime 与页面捕获时刻可能跨分钟，按原样精确匹配 dedupKey 会漏。通知先到→页面捕获命中邻近分钟条目→只回填收款方/支付方式（富化，不入新条目）；页面先到→通知捕获跳过。同一笔交易"通知+页面+悬浮确认"三通道最终只入账一次（悬浮确认 externalId 仍是 `NTF:`+dedupKey，撞唯一索引时提示"已入账"）。
- **dedupKey 分钟桶对齐交易时间**：页面有交易时间时用交易时间的分钟（与该笔支付通知的 postTime 分钟天然一致），无则用捕获时刻。
- **页面快照不落库噪音**：只有解析命中或含支付关键词（`looksInteresting`）的页面才进捕获日志，聊天/朋友圈浏览不刷爆 7 天/2000 条的日志表；debug 开关打开时全量落库用于采样。入队 note 只存"支付方式 X"等提取字段，**不存整页文本**（页面可能含卡号/余额）。
- **事件风暴四道闸**：config 限包名+事件类型（系统级）→ notificationTimeout=300ms → 400ms 防抖合并 → 页面文本指纹去重（同内容只解析一次，顺带挡"翻回同一笔账单"）。
- **跳过场景（宁漏勿错）**：退款页/收入页（"已存入零钱"、非"对方已收钱"的"已收钱"）暂不入队——通知通道与账单导入已覆盖退款与收入；超 24 小时的旧账单详情不入队（防翻旧账产生垃圾条目）。
- **状态行陷阱**："对方已收钱"是微信转账**支出**的状态、转账支出页也有"收款方"标签——方向判定里"对方已收钱"单独算支出，且"标签→值"提取带状态短语守卫，防止把"已收钱"当收款方。
- **Room v4→v5**：captured_notifications 加 `source` 列（NOTIFICATION/A11Y），defaultValue 与实体 `@ColumnInfo` 声明一致，迁移 SQL 与导出 schema 5.json 逐字核对过。

### 踩坑

- Kotlin 局部函数不能直接当值传递（`cyclerRow(..., dp, ...)` 报错），改 `val dp: (Int) -> Int = {...}`。
- `suspend` DAO 不能在非 suspend 函数里调用：`maybeShowFloatingConfirm` 被标记为 `suspend`（其调用点在协程内）。
- 无焦点窗口里 Spinner 弹层不可用 → 悬浮窗选择器用 ‹ › 步进；`NOT_FOCUSABLE` 同时保证无障碍的 `rootInActiveWindow` 仍指向支付页。

### 用户实测的四条样本与失败原因

| 通知原文 | 旧引擎结果 | 原因 |

| 微信 text=已支付¥12.80 | 未识别 | 支出关键词没有"已支付"，且金额是 ¥ 前缀（关键词后无数字） |

### 修改

- **方向判定重构**：退款（退款/退回）优先于收/支判定——"退款到账"同时命中"到账"不能当普通收款；双向命中仍放弃。新增支出关键词：已支付、支付成功（注意不能加裸"支付"——微信收款通知里的"微信支付"会让收支双向命中）。
- **金额提取三层**：正向（关键词后跟数字）→ 反向（数字+元+关键词，覆盖"14.90元的支出/退款"）→ ¥ 金额兜底（已支付¥12.80 / 收款金额¥0.01）。
- **退款入账口径**：待确认队列表新增 refundMark 列（Room v3→v4 迁移；实体用 @ColumnInfo(defaultValue="NONE") 让新建库与迁移库 schema 逐字一致），确认入账时退款收入打 REFUND_INCOME——与账单导入口径一致，"显示退款记录"开关对捕获记录同样生效。

## 2026-10-05 · 退款记录显示开关（"显示退款记录"）

### 需求

默认不显示退款（与原行为一致）；设置中开启"显示退款记录"后：退回的金额标记「退款收入」、被全额退款的支出标记「已退款」，计入总收支并额外显示「已取消收支」合计；关闭则不显示、不计入。

### 关键设计决策

- **退款记录始终入库、开关只控制显示与统计**（而不是解析时决定是否入库）：切换开关立即对全部历史导入生效，无需重新导入账单。数据库中多存的数据只是带标记的正常交易记录。
- **无需合成记录**：真实账单中微信退款本来就是成对的两行——退款到账行（收/支=收入、交易类型"XXX-退款"、状态"已全额退款"/"已退款(¥8.54)"）+ 原支出行；支付宝为"交易关闭"支出行 + "退款成功"不计收支行。解析时打标记即可。
- **部分退款的支出不打"已退款"标记**：微信原支出行状态"已退款(¥8.54)"（兼容"已退款¥8.54"）时保持普通支出（净支出本来就该是全额），退款额由独立收入行承载；支付宝部分退款原行状态仍"交易成功"，同理。
- **「已取消收支」= 退款到账金额合计**（收入侧）：全额退款时与已退款支出合计一致；部分退款时即为实际退回金额。
- 微信账单里"对方名-退款"是交易类型列的特征，交易对方列是干净商户名，分类猜测不受影响。

### 实现

- 数据层：`RefundMark` 枚举（NONE/REFUNDED_EXPENSE/REFUND_INCOME）新增到交易表；数据库 v1→v2 迁移（ALTER TABLE 加列，保留用户已导入数据）；所有月度查询（流水/收支汇总/分类占比/账户余额）加 `includeRefunds` 参数，余额查询把过滤条件放进 LEFT JOIN 的 ON 子句避免丢掉无交易账户；新增退款合计查询。
- 设置存储：SharedPreferences（"显示退款记录"布尔值），ViewModel 持有状态流，各查询流用 combine 联动开关。
- UI：设置页开关（含说明文案）；流水/统计页汇总行开启时显示第 4 列「已取消」；流水列表与导入预览的退款行显示「退款收入」/「已退款」角标；导入预览显示"退款相关 N 条"及当前开关状态提示。
- 「已取消收支」列不受开关外的其他过滤影响，仅由开关决定是否展示。

### 真实文件验证

- 微信 xlsx：**190 条全部入库**（原 157 条有效 + 33 条退款相关），中性交易仍跳过 2 条；dump 可见成对记录（姜胖胖：退款收入 50 元与原支出 50 元，时间一前一后）。
- 支付宝 CSV：**458 条入库**（444 普通 + 7 交易关闭 + 7 退款收入）+ 3 条不计收支跳过 = 官方总数 461 笔；Steam 两笔退款收入（34.80/24.48）正确识别。
- 25 个单元测试全部通过（更新微信旧版/新版 xlsx、支付宝 2026 用例覆盖全额/部分退款标记）。

### 踩坑

- 带过滤条件的 LEFT JOIN 若把条件放 WHERE，无交易的账户会因 NULL 比较被整体过滤掉，必须放在 ON 子句。
- 旧数据升级：Room 迁移列必须带 NOT NULL DEFAULT，且枚举列以字符串形式存储（Room 默认按枚举名转换）。

  - 交易时间是 Excel 日期序列号（如 46299.627337962964），换算 = (序列号 − 25569) 天 + 小数部分×86400 秒；文件注明为 UTC+8 墙上时间，按本地时区转毫秒，与 CSV 路径语义一致；
  - 金额是无 ¥ 前缀的纯数字单元格；"不计收支"改称**"中性交易"**；
  - 表头列名不变，表头前同样有说明行。
- **支付宝 2026 版 CSV 表头大改**：
  - 列为：交易时间,交易分类,交易对方,对方账号,商品说明,收/支,金额,收/付款方式,交易状态,交易订单号,商家订单号,备注（旧版的 交易创建时间/付款时间/金额（元）/交易号 已不存在）；
  - 新增**"交易分类"列**（餐饮美食/日用百货/文化休闲…），可直接映射应用分类；
  - 交易订单号/商家订单号单元格带**尾部制表符**（trim 掉）；
  - 存在"交易关闭"的支出行，与其后"退款成功"的不计收支行成对出现，两者都跳过才不会重复；
  - 一笔可用组合支付方式（"中国银行储蓄卡(8920)&大牌补贴立减"）。

### 决策记录

- **金额一律用"分"（Long）存储**，避免浮点误差；`Money` 工具类统一解析与展示。
- **CSV 编码识别**：先 UTF-8 严格解码，失败回退 GBK；另外加了"含『交易』关键词"校验——GBK 字节序列偶发能被 UTF-8 解码成乱码而不报错，仅靠异常判断不可靠。
- **解析器用列名映射而非固定列位**：微信/支付宝改版调整列顺序时不至于直接失效。
- **退款行跳过**：微信"已全额退款"状态行、支付宝未完成（如等待付款）行不导入，避免净额重复；跳过数量在预览页明示。
- **UI 全部用 Material 3 默认样式**，按约定阶段一不做视觉打磨。
- **ViewModel 全局一个**（LedgerViewModel）：月份切换是流水/统计共享状态，且数据量级小，简单优先；后续阶段按需拆分。

### 踩坑（编译期）

- `stickyHeader` 自 foundation 1.7 起是 `LazyListScope` 接口的成员函数，不能（也不需要）import，写 import 反而报 Unresolved reference。
- Kotlin 不允许 `continue` 出现在 `run { }` 这类内联 lambda 中（实验特性默认关闭），"解析失败就 continue"要写成显式的 `if (x == null) { ...; continue }`。
- Material 3 的 `@OptIn(ExperimentalMaterial3Api::class)` 别忘了 import 注解类本身，报错形式是"Unresolved reference 'ExperimentalMaterial3Api'"。
- `AppLog` 直接调 `android.util.Log`，JVM 单元测试里会抛 "not mocked"，需在 `app/build.gradle.kts` 加 `testOptions { unitTests.isReturnDefaultValues = true }`。

### 踩坑（测试期）
