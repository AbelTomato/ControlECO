## 2026-10-08 · 首页模式①月份细环口径反转（已过 → 剩余）+ 环内剩余天数

### 需求（用户反馈）

"月份内圈是否绘制反了？这个月才过去八天但圆环只剩下 1/4。"

### 排查与决策

不是算错，是**两条环的口径相反**：主环饱和度高的弧 = 预算**剩余**（69%），而细环饱和度高的弧 = 本月**已过**（8/31 = 25%）—— 同一种视觉语言在同一格里表达相反含义，读起来就像"只剩 1/4"。而且主环读"还剩多少"、细环读"过了多少"，根本无法直接比长短。

改为**两环同口径（都表示"还剩多少"）**：细环改画本月剩余（`1 − dayOfMonth/lengthOfMonth`，10 月 8 日 = 23/31 ≈ 74%），已过部分留在浅蓝底轨上。这样一眼就能对比：蓝弧比绿弧短 = 花钱比时间快（截图里绿 69% 略短于蓝 74%，正是本月花钱略快）。环内补一行 `本月剩余 23 天`，把口径写死，避免再被读反。

### 验证

- `:app:assembleDebug :app:testDebugUnitTest` 通过（88 tests，0 failures；本轮为绘制口径调整，无纯函数改动）。
- 实机截图确认：细环约 3/4 圈，环内显示"本月剩余 23 天"，与 `31 − 8` 一致。

## 2026-10-08 · 账单/统计加缓存 + 账单页紧凑头部与滑动条 + 月份选择面板

### 需求（用户反馈）

每次打开账单/统计都"从空闪到满"（怀疑没做缓存）；账单页上方区域压窄让列表更大、右侧要滑动条；再次点 tabbar「账单」回到顶部；当前月份与日期切换"太差劲（纯列表）"需美化。

### 实现

1. **数据缓存（不再闪空）**：`monthRows` / `monthTotals` / `expenseByCategory` / `refundIncomeTotal` 原本是**冷 Flow**，UI 用 `collectAsStateWithLifecycle(initialValue = emptyList())` 收集 —— 每次切标签页都重新订阅、初始值是空表，于是"空 → 满"闪一下，且每次都要重建 Room 观察。改为 `stateIn(viewModelScope, WhileSubscribed(5_000), …)` 的 **StateFlow**：切回来立刻拿到上次结果、后台再刷新；没有订阅者 5 秒后自动停掉 Room 观察（省电省查询）。两个页面改为直接收 StateFlow。
2. **账单页头部压缩（列表区上移约 80dp）**：标题行与月份行整体缩高（⋮ 40dp、切月箭头 34dp）；「本月支出」字号 `displaySmall → headlineLarge`，**收入/结余竖排到右侧**同一行（省下一整行）；记录数提示挪到月份行右侧；「汇总为整月数据」并入筛选胶囊行右端。
3. **右侧滑动条**：Compose 的 `VerticalScrollbar` 只存在于桌面版 foundation，Android 端没有 → 自绘 `ListScrollbar`：可见条目占比 → 拇指长度、首条目位置 → 拇指位置（首尾严格对齐），拇指可拖动跳转（18dp 触摸热区 + 5dp 视觉宽，静止 22% 透明度、按住 50%）。踩了两个坑：①判据用"条目数是否超过可见数"会让"最后一条只露一半"不显示 —— 改用 `canScrollForward/canScrollBackward`；②测量用的 `onSizeChanged` 挂在会提前 `return` 的节点上，高度永远是 0，滑动条永不出现 —— 改为始终发射容器、内部按条件画拇指。
4. **重按标签回顶**：`AppNav` 里重按当前标签时 `reenterTick++`，传给账单页（`LazyListState.animateScrollToItem(0)`）与统计页（`ScrollState.animateScrollTo(0)`），切月时账单列表也回到顶部。
5. **月份/日期切换美化**：月份胶囊由"一长串下拉菜单"改为 **底部月份选择面板**（`ModalBottomSheet`：年份左右步进 + 4×3 月份格子，选中浅蓝实底、本月描边、右上「回到本月」）；日期分组头由纯文本行改为**胶囊 chip**（今天/昨天浅蓝实底，其余白底描边），右侧仍是当天小计。

## 2026-10-08 · 翻转灵敏度与立体感 + 模式②环内去百分比 + K/M/B 逐档进位修正

### 需求（用户反馈）

调高首页滑动灵敏度（当前翻转"很薄"，要一点立体感）；模式②圆环内不要显示百分比；K/M/B 只有 K 遵循了"小数点前超过 4 位（不含 4 位）才进位"的规则，M、B 需修正。

### 实现

1. **滑动更跟手**：比例由 `90° / 45% 卡片宽` 收紧到 `90° / 30% 卡片宽`（常量 `DRAG_FULL_TURN_WIDTH_FRACTION`），同样手指位移转得更多；再加**快速甩动**通道——`VelocityTracker` 记录指尖速度，速度 ≥ 1.1 卡片宽/秒（`FLICK_WIDTHS_PER_SECOND`）即翻页，不必等角度到 45°。角度与速度都启动时按跟手旋转方向走，只有快甩才用速度方向，方向永远与手指一致。
2. **立体感（全部在 `graphicsLayer` 的 draw 阶段读值，零重组）**：翻转进度 `p = |rotationY| / 90`，随 p 变化三件事——`cameraDistance` 从 14×density 收到 6×density（越接近侧立**透视越强**，此前 14 恒定偏"平"）、整体 `scale` 收到 0.94（轻微后退）、`alpha` 降到 0.8（受光面偏离变暗）。三者叠加读起来像一张卡片翻过去，而不是平面瞬间换内容。
3. **模式②环内去掉百分比**：`CategoryRing` 删除 `labelSmall` 的 `"$percent%"` 与配套的 `percent` 计算，环内只留分类名 + 剩余金额（心跳警示仍挂在金额上）。
4. **K/M/B 逐档进位修正**：原实现按固定金额阈值（≥1 万 K、≥100 万 M、≥10 亿 B）换挡，导致 M 提前出现（如 ¥1,234,567.89 显示 ¥1.23M，而按规则 K 档显示值 1234.57 仍是 4 位、不该进位）。改为**按最终显示文本判断**：K → M → B 逐级尝试，`小数点前位数 ≤ 4` 即停档（例：¥1,234.12 原样；¥32,312.32 → ¥32.31K；¥1,000,000 → ¥1000K；¥12,345,678.9 → ¥12.35M；¥9,999,999.99 因四舍五入成 10000K 而继续进到 ¥10M）。`COMPACT_UNITS` 常量表驱动，档位与规则单一来源。

### 验证

- `:app:assembleDebug :app:testDebugUnitTest` 通过（85 tests，0 failures）。
- `MoneyTest` 重写紧凑金额用例：4 位不进档（¥1,234.12 / ¥9,999.99）、K 档 4 位不进 M（¥1000K / ¥1234.57K）、M 档 4 位不进 B（¥12.35M）、负数符号、以及四舍五入跨档边界（9,999,999.99 → ¥10M、9,999,990 → ¥9999.99K）。
- 真机走查：灵敏度（30% 宽 ≈ 90°、甩动阈值 1.1 宽/秒）、立体感强度（`cameraDistance` 14→6、scale 0.94、alpha 0.8 三处常量可调）。

## 2026-10-08 · 翻转交互修正（滑动跟手/方向一致）+ 月份环提饱和 + 无预算保留三模式

### 需求（用户反馈）

翻转方向与滑动方向不一致，且模式②"概率无法滑动翻转"；月份环看起来像灰色（要提高不透明度与饱和度）；未设置预算时首页只剩一个模式，应保留三个模式，模式①②提示设置预算。

### 实现

1. **滑动翻转重做（方向一致 + 模式②可靠）**：
   - 由"只能点击翻转"改为**跟手翻转**：`detectHorizontalDragGestures` 累计拖拽 → 旋转角度直接跟手（`90° / 45% 屏宽` 的比例），越过 45° 阈值在手指方向上继续翻到 90°、换内容、从 −90° 转回；未越过则回弹。完成动画从手指停下的角度继续、同一方向，**方向与手势天然一致**。
   - 点击/圆点沿用同一方向约定："下一个 = 负向旋转"，`(t−mode+3)%3` 识别前后方向；防重入（`flip.isRunning`）；减少动画时瞬时切换。
   - 模式②"概率无法滑动"的根因是与网格纵向滚动争手势：现只在内容溢出时才给网格挂 `verticalScroll`，常规情况无竞争；溢出时按方向由系统 slop 判定分流。
   - 拖拽回调经 `rememberUpdatedState` 取最新闭包，避免捕获过期的"减少动画"状态。
2. **月份环提饱和**：轨道 = `primary` 22% 透明，进度弧 = `primaryStrong`（新增的饱和蓝 token）满不透明——此前 `primaryContainer` + 55% 透明在浅底上呈灰调。
3. **无预算保留三模式**：移除整页的 `NoBudgetContent`，模式机器（月份胶囊/待确认/圆点/翻转）始终可用；模式①展示占位环 +"还没有设置月预算"+"设置月预算后，这里显示本月还可以花与本日剩余"+ 设置按钮；模式②展示"还没有分类预算"并指引到分类管理；模式③无需预算照常显示本月已花（墨色、无警示色）与总存款。设置弹窗回到主布局统一处理。

### 验证

- `:app:assembleDebug :app:testDebugUnitTest` 通过（84 tests，0 failures；本轮无纯函数改动）。
- 真机走查：跟手翻转手感（0.45 屏宽 ≈ 90°、45° 阈值）、方向是否符合直觉（若不合适只需在 `flipTo`/`onDragEnd` 中翻转 sign）、月份环蓝色深浅（`primaryStrong` 与 22% 轨道）。

## 2026-10-08 · 圆环细节重做（偏移修复/时间环/K·M·B/心跳警示）+ 模式②其他环 + 白+浅蓝主题

### 需求（用户逐条反馈）

模式②除已设预算的分类外，"其他"剩余预算与支出归为一个"其他"环（仅预览，不改账单页）；圆环颜色弧与灰轨道有偏移（bug）、圆角过于圆润改小、环内金额多时与环重叠（需缩放 + K/M/B 单位 + 间隔）；百分比前去掉"剩余"二字；模式②要浅灰轨道；提示色绿蓝红 → **绿黄红**；背景暖金 → **白色 + 浅蓝**；模式①内套一个很细的时间环（本月过了多少，与预算对照）且大环再放大；"记一笔"改短；所有超支红饱和度加高，红色数字加"心跳 + 间隔性快速轻摇"警示（剩余越少/超支越多越强越快越艳，需设上限）；模式②不再截断 4 个，弹性塞入全部。

### 实现

1. **偏移 bug 根因与修复**：`drawArc` 默认包围盒 = 整个画布，弧的中心线半径 = min/2；而轨道用 `radius = (min − stroke)/2` 绘制，二者中心线差 stroke/2 → 弧整体外偏。修复：弧改用 `topLeft = center − r、size = 2r（r = 中心线半径）`，与轨道完全同几何（模式①②都改）。
2. **圆角改小**：弧/环取消 `StrokeCap.Round` 改用默认平头（25dp 粗描边的圆头端过于圆润）。
3. **模式①（更大 + 时间环）**：环尺寸自适应 `min(可用宽×0.84, 可用高×0.58)` 夹在 200–290dp；内圈再画一条 4dp 细环 = 本月已过比例（`dayOfMonth / lengthOfMonth`，灰调），与预算进度直接对照；百分比只显示"42%"（去掉"剩余"）。
4. **金额显示（K/M/B + 自适应缩放）**：新增 `Money.formatYuanCompact`——整数部分 ≤4 位正常分组（¥1,234.12），超过 4 位进位 K/M/B，两位小数去尾零（¥32.31K / ¥10K / ¥1.23M / ¥12.35B），负数保留符号；环内金额用新 `AutoScaledText`：超出可用宽度按比例缩字号（下限 0.55×），环内文字宽度预留心跳放大余量，不与环重叠。
5. **模式②（其他环 + 弹性网格）**：
   - `buildCategoryRings` 新增"其他"聚合环：预算 = 月总预算 − 已分配分类预算；支出 = 当月总支出 − 已计入分类环的支出 → **Σ分类剩余 + 其他剩余 = 月总剩余**（与模式①口径一致，有单测守恒断言）。无任何分类预算时"其他"即全部（此时显示一句设置引导）；全部分类预算超过总预算（其他预算 ≤ 0）时不出其他环。
   - 取消 `.take(4)`：按环数选列数（≤2 一列排、3–4 两列、5–9 三列、10+ 四列），环径取 宽/高 双约束的较小者（68–124dp）自适应缩放，超长时整列可滚动——弹性容纳全部圆环。
   - 每环补浅灰轨道（hairline），与弧同几何。
6. **警示色与心跳**（`warningSeverity` 纯函数 + `Modifier.warningHeartbeat`）：
   - 档位色改 **绿（≥50%）/ 黄（20–50%，warning 琥珀）/ 红（<20%）**；红档随强度从 `critical` 向新的 `criticalAlert`（饱和度最高的警报红）插值。
   - 强度 = `(0.2 − 剩余比例) / 0.5` 夹 0..1：红档起点 0、超支 30% 封顶 1。
   - 心跳 = 缩放 1.0→(1+0.10×强度) 的脉冲，周期 1400→650ms（随强度加快），每次脉冲后留休息；摇晃 = 每 2.6s 一小段 3 次快速轻摆（幅度 ≤2.2°）——上限即"防止过度动画"。
   - 应用：模式①环内金额+百分比块、超支大字；模式②每环金额+百分比块；模式③本月已花（红档）与负总存款。连续动画只在 draw 阶段读取（graphicsLayer），零重组；系统"减少动画"时不播放。
   - `critical` 本体也提高饱和度（浅色 0xFFA5402C→0xFFC1352B，深色 0xFFE9886F→0xFFF07C64），error 色同步。
7. **主题：白 + 浅蓝**：浅色 background/surface 纯白，容器/描线/次级色全部改为冷蓝灰（surfaceContainer 0xFFF3F7FB、hairline 0xFFE3EAF1、onSurface 0xFF1B2430 等）；深色套改为冷底（0xFF12161C/0xFF171C23）；分类调色板替换掉暖金/驼色系为冷调八色。

## 2026-10-06 · 悬浮窗不弹的根因修复 + 捕获日志分通道 + USB 调试指南

### 用户反馈：支付页面出现但悬浮确认窗没有弹出

**根因（设计缺陷，已修）**：通知通道先入队时，页面捕获命中 ±1 分钟邻键条目 → 走"富化"路径后直接 return——**悬浮窗被富化路径抑制了**。只要通知监听正常工作，悬浮窗就永远不会弹，与验收标准"微信扫码付款 → 悬浮窗弹出"矛盾。修复：富化后照常弹出悬浮窗（支付瞬间给确认窗是正确的产品形态），**去重闸门移到入账时**——悬浮确认的 externalId 唯一索引兜底 + 确认/忽略时同时清理精确 dedupKey 与 ±1 分钟邻键的待确认条目（`deletePendingFor`），保证三通道仍只入账一次。

- `floating confirm disabled`——设置页开关关着
- `floating confirm skipped (no overlay permission)`——未授权"显示在其他应用上层"

- `floating confirm shown`——已尝试弹出（若仍看不到 → 支付保护中心/支付保险箱拦截，见保活页）
- 页面连快照都没有 → 无障碍事件未到达（受限设置未解锁/服务未开），先看 `snapshot`/`skip (not a payment page)` 日志

## 2026-10-06 · 阶段三：无障碍页面采集 + 悬浮确认窗 + 权限引导补全

### 实现内容（对照交接文档四项目标）

1. **无障碍服务骨架**：`AccBookAccessibilityService` + `res/xml/accessibility_service_config.xml`。事件只订阅 `TYPE_WINDOW_STATE_CHANGED|TYPE_WINDOW_CONTENT_CHANGED`、包名限定微信/支付宝、只读窗口内容、不申请手势能力（最小权限）。服务连接状态经 `CaptureCenter.a11yConnected` 状态流暴露给设置页/保活页；`isEnabled()` 读 `Settings.Secure.ENABLED_ACCESSIBILITY_SERVICES` 检测（保活页与设置页的"去开启"跳 `ACTION_ACCESSIBILITY_SETTINGS`）。
2. **页面识别规则**（`PageRules.kt`，风格对齐 NotificationRules，纯函数可单测）：输入=包名+页面文本快照（text/contentDescription 按控件树顺序，不依赖 viewId）。识别「支付成功页」（支付成功/付款成功/支付完成）与「账单详情页」（账单详情/交易详情），提取金额（标签行→独立 ¥ 节点→任意 ¥ 三层）、收款方/商家、支付方式、交易时间。
3. **悬浮确认窗**（`FloatingConfirmWindow.kt`）：`TYPE_APPLICATION_OVERLAY` + `NOT_FOCUSABLE|NOT_TOUCH_MODAL`；经典 View 实现（Compose 在 overlay 窗口需手工接 LifecycleOwner，不值得）；分类/账户用 ‹ › 循环选择（Spinner 弹层在无焦点窗口不可用）；确认直接入账并清同笔待确认；90 秒自动消失；忽略=删除同笔待确认条目。`SYSTEM_ALERT_WINDOW` 权限，设置页引导跳 `ACTION_MANAGE_OVERLAY_PERMISSION`。
4. **权限引导补全**：设置页加无障碍采集状态卡+开关、悬浮确认窗授权卡+开关；保活页加无障碍状态行 + **安卓 13+ 侧载"允许受限制的设置"通用第一步卡**（红色标题置顶）；分品牌补支付保护拦截对策（小米支付保险箱、荣耀支付保护中心、OPPO 系支付保护，华为已有）。

### 关键设计决策

- **跨通道去重改为 ±1 分钟容错**（`findRelatedPending`）：通知 postTime 与页面捕获时刻可能跨分钟，按原样精确匹配 dedupKey 会漏。通知先到→页面捕获命中邻近分钟条目→只回填收款方/支付方式（富化，不入新条目）；页面先到→通知捕获跳过。同一笔交易"通知+页面+悬浮确认"三通道最终只入账一次（悬浮确认 externalId 仍是 `NTF:`+dedupKey，撞唯一索引时提示"已入账"）。
- **dedupKey 分钟桶对齐交易时间**：页面有交易时间时用交易时间的分钟（与该笔支付通知的 postTime 分钟天然一致），无则用捕获时刻。
- **页面快照不落库噪音**：只有解析命中或含支付关键词（`looksInteresting`）的页面才进捕获日志，聊天/朋友圈浏览不刷爆 7 天/2000 条的日志表；debug 开关打开时全量落库用于采样。入队 note 只存"支付方式 X"等提取字段，**不存整页文本**（页面可能含卡号/余额）。
- **事件风暴四道闸**：config 限包名+事件类型（系统级）→ notificationTimeout=300ms → 400ms 防抖合并 → 页面文本指纹去重（同内容只解析一次，顺带挡"翻回同一笔账单"）。
- **跳过场景（宁漏勿错）**：退款页/收入页（"已存入零钱"、非"对方已收钱"的"已收钱"）暂不入队——通知通道与账单导入已覆盖退款与收入；超 24 小时的旧账单详情不入队（防翻旧账产生垃圾条目）。
- **状态行陷阱**："对方已收钱"是微信转账**支出**的状态、转账支出页也有"收款方"标签——方向判定里"对方已收钱"单独算支出，且"标签→值"提取带状态短语守卫，防止把"已收钱"当收款方。
- **Room v4→v5**：captured_notifications 加 `source` 列（NOTIFICATION/A11Y），defaultValue 与实体 `@ColumnInfo` 声明一致，迁移 SQL 与导出 schema 5.json 逐字核对过。

### 踩坑

- Kotlin 局部函数不能直接当值传递（`cyclerRow(..., dp, ...)` 报错），改 `val dp: (Int) -> Int = {...}`。
- `suspend` DAO 不能在非 suspend 函数里调用：`maybeShowFloatingConfirm` 被标记为 `suspend`（其调用点在协程内）。
- 无焦点窗口里 Spinner 弹层不可用 → 悬浮窗选择器用 ‹ › 步进；`NOT_FOCUSABLE` 同时保证无障碍的 `rootInActiveWindow` 仍指向支付页。

## 2026-10-06 · 通知规则引擎适配真实付款/退款通知（用户实测样本）

### 用户实测的四条样本与失败原因

| 通知原文 | 旧引擎结果 | 原因 |
|---|---|---|
| 微信 text=已支付¥12.80 | 未识别 | 支出关键词没有"已支付"，且金额是 ¥ 前缀（关键词后无数字） |

| 支付宝 text=你有一笔14.90元的支出… | 未识别 | **金额在关键词前面**（"14.90元的支出"），旧正则只找"关键词后的金额" |

### 修改

- **方向判定重构**：退款（退款/退回）优先于收/支判定——"退款到账"同时命中"到账"不能当普通收款；双向命中仍放弃。新增支出关键词：已支付、支付成功（注意不能加裸"支付"——微信收款通知里的"微信支付"会让收支双向命中）。
- **金额提取三层**：正向（关键词后跟数字）→ 反向（数字+元+关键词，覆盖"14.90元的支出/退款"）→ ¥ 金额兜底（已支付¥12.80 / 收款金额¥0.01）。
- **退款入账口径**：待确认队列表新增 refundMark 列（Room v3→v4 迁移；实体用 @ColumnInfo(defaultValue="NONE") 让新建库与迁移库 schema 逐字一致），确认入账时退款收入打 REFUND_INCOME——与账单导入口径一致，"显示退款记录"开关对捕获记录同样生效。
- **去重键升级**：加入方向与退款标记（pkg|INCOME|R|1490|分钟），同一分钟内同额的"支出+退款"不再互相吞掉。

## 2026-10-05 · 退款记录显示开关（"显示退款记录"）

### 需求

默认不显示退款（与原行为一致）；设置中开启"显示退款记录"后：退回的金额标记「退款收入」、被全额退款的支出标记「已退款」，计入总收支并额外显示「已取消收支」合计；关闭则不显示、不计入。

### 关键设计决策

- **退款记录始终入库、开关只控制显示与统计**（而不是解析时决定是否入库）：切换开关立即对全部历史导入生效，无需重新导入账单。数据库中多存的数据只是带标记的正常交易记录。
- **无需合成记录**：真实账单中微信退款本来就是成对的两行——退款到账行（收/支=收入、交易类型"XXX-退款"、状态"已全额退款"/"已退款(¥8.54)"）+ 原支出行；支付宝为"交易关闭"支出行 + "退款成功"不计收支行。解析时打标记即可。
- **部分退款的支出不打"已退款"标记**：微信原支出行状态"已退款(¥8.54)"（兼容"已退款¥8.54"）时保持普通支出（净支出本来就该是全额），退款额由独立收入行承载；支付宝部分退款原行状态仍"交易成功"，同理。
- **「已取消收支」= 退款到账金额合计**（收入侧）：全额退款时与已退款支出合计一致；部分退款时即为实际退回金额。
- 微信账单里"对方名-退款"是交易类型列的特征，交易对方列是干净商户名，分类猜测不受影响。

### 实现

- 数据层：`RefundMark` 枚举（NONE/REFUNDED_EXPENSE/REFUND_INCOME）新增到交易表；数据库 v1→v2 迁移（ALTER TABLE 加列，保留用户已导入数据）；所有月度查询（流水/收支汇总/分类占比/账户余额）加 `includeRefunds` 参数，余额查询把过滤条件放进 LEFT JOIN 的 ON 子句避免丢掉无交易账户；新增退款合计查询。
- 设置存储：SharedPreferences（"显示退款记录"布尔值），ViewModel 持有状态流，各查询流用 combine 联动开关。
- UI：设置页开关（含说明文案）；流水/统计页汇总行开启时显示第 4 列「已取消」；流水列表与导入预览的退款行显示「退款收入」/「已退款」角标；导入预览显示"退款相关 N 条"及当前开关状态提示。
- 「已取消收支」列不受开关外的其他过滤影响，仅由开关决定是否展示。

### 真实文件验证

- 微信 xlsx：**190 条全部入库**（原 157 条有效 + 33 条退款相关），中性交易仍跳过 2 条；dump 可见成对记录（姜胖胖：退款收入 50 元与原支出 50 元，时间一前一后）。
- 支付宝 CSV：**458 条入库**（444 普通 + 7 交易关闭 + 7 退款收入）+ 3 条不计收支跳过 = 官方总数 461 笔；Steam 两笔退款收入（34.80/24.48）正确识别。
- 25 个单元测试全部通过（更新微信旧版/新版 xlsx、支付宝 2026 用例覆盖全额/部分退款标记）。

### 踩坑

- 带过滤条件的 LEFT JOIN 若把条件放 WHERE，无交易的账户会因 NULL 比较被整体过滤掉，必须放在 ON 子句。
- 旧数据升级：Room 迁移列必须带 NOT NULL DEFAULT，且枚举列以字符串形式存储（Room 默认按枚举名转换）。

## 2026-10-05 · 适配 2026 版微信/支付宝真实账单格式（用户提供 docs/book 实测文件）

### 发现（真实导出与假设差异很大）

- **微信："用于个人对账"导出已从 CSV 改为 xlsx**：
  - 交易时间是 Excel 日期序列号（如 46299.627337962964），换算 = (序列号 − 25569) 天 + 小数部分×86400 秒；文件注明为 UTC+8 墙上时间，按本地时区转毫秒，与 CSV 路径语义一致；
  - 金额是无 ¥ 前缀的纯数字单元格；"不计收支"改称**"中性交易"**；
  - 表头列名不变，表头前同样有说明行。
- **支付宝 2026 版 CSV 表头大改**：
  - 列为：交易时间,交易分类,交易对方,对方账号,商品说明,收/支,金额,收/付款方式,交易状态,交易订单号,商家订单号,备注（旧版的 交易创建时间/付款时间/金额（元）/交易号 已不存在）；
  - 新增**"交易分类"列**（餐饮美食/日用百货/文化休闲…），可直接映射应用分类；
  - 交易订单号/商家订单号单元格带**尾部制表符**（trim 掉）；
  - 存在"交易关闭"的支出行，与其后"退款成功"的不计收支行成对出现，两者都跳过才不会重复；
  - 一笔可用组合支付方式（"中国银行储蓄卡(8920)&大牌补贴立减"）。

### 修改

- 新增 `XlsxReader`：正则解析 xlsx 的 sharedStrings 与第一个工作表（零依赖、可在 JVM 单测运行），支持共享字符串/内联字符串/数值单元格、缺失单元格补空、AA 以后的列号、XML 实体反转义。
- `BillParsers.parse` 按 zip 魔数(PK)嗅探 xlsx 与 CSV；`parseWechat` 时间兼容序列号；`parseAlipay` 按新表头重写、旧表头自动兼容（付款时间优先于创建时间仍保留）。

- 界面文案更新导出格式说明（微信 xlsx / 支付宝 CSV）。
- 新增 `RealFileParseCheck` 手动核对工具：格式再变时把新导出文件放 docs/book，跑 `--tests "*RealFileParseCheck*"` 打印解析结果人工比对。

### 决策记录

- **金额一律用"分"（Long）存储**，避免浮点误差；`Money` 工具类统一解析与展示。
- **CSV 编码识别**：先 UTF-8 严格解码，失败回退 GBK；另外加了"含『交易』关键词"校验——GBK 字节序列偶发能被 UTF-8 解码成乱码而不报错，仅靠异常判断不可靠。
- **解析器用列名映射而非固定列位**：微信/支付宝改版调整列顺序时不至于直接失效。
- **退款行跳过**：微信"已全额退款"状态行、支付宝未完成（如等待付款）行不导入，避免净额重复；跳过数量在预览页明示。
