## 2026-10-07 · 首页资源池改为人民币纸币堆（金币效果返工）

### 用户反馈与需求

金币效果不佳，改为**纸币**：人民币样式、简单几何 + 不同颜色与大小表示面额；动画全部改为原地发生（不再从顶部掉落）——收入纸币直接出现、支出抽出纸币后消散；大额用堆叠的 ¥100 表示 1k/1w 以控制绘制压力。

### 实现（CashPile.kt 替代 CoinPile.kt，967e976）

1. **纸币绘制**：`drawBanknote` 纯几何——投影/底色/细描边/内面版面/圆形印章/顶边高光/面额数字；票面 2.08:1 贴近真币比例。面额色按 2019 版人民币低饱和化（1 橄榄/5 紫/10 蓝/20 棕/50 绿/100 红），`NoteColor(base/deep/face)` token 放入 Theme.kt 明暗两套（维持硬编码色只在主题文件的验收线）。
2. **资源池 = 3 叠 × 8 张（容量 24）**：填充序号交错分配（i→叠 i%3、层 i/3），数量增减 = 整排一起长/拆（抽走总是每叠顶层各一张，三叠对称消减）；各叠顶张画面额数字、下层只画色块（省 drawText）。
3. **动画全部原地发生**：入场/后台恢复 = formPile 逐张原地弹出（scale+alpha+轻微沉降，pop 完成→堆数量+1→无缝交接堆本体）；支出 = 抽出（上移 36–96dp+微倾斜+轻微放大，后 45% 淡出消散，力度随金额/预算比例）；收入 = 直接出现（新槽位 pop，hold 至堆数量动画追平后淡出；堆满时顶部示意性弹出）。
4. **面额计划**：`settlementNotePlan`——≥100 元→3–8 张 ¥100（堆叠的 100 表示 1k/1w）；20–99 元→1–3 张 ¥20；10/5/1→对应面值单张。不同面值的颜色与大小只在小额收支出现。

### 决策与踩坑

- **保留 45c0821 的架构改进**：`remainingToPileCount` 对数规模映射、ON_RESUME 重建堆、快照消费即记录、粒子 finally 释放——纸币化只替换视觉层与动画形态，状态机/数字滚动/±¥横幅/Reduced Motion/动画开关不动。
- **收入粒子交接时序**：粒子不能 pop 完立即消失（堆数量 tween 还没追到该槽位会闪断）——引入 holdMs（堆动画时长 − pop 时长），粒子保持到堆本体接手后再淡出。
- 面额数字用 Compose TextMeasurer 按 6 面值缓存 TextLayoutResult，每帧最多 3 次 drawText（仅各叠顶张）；零临时对象、零重组的性能架构不变。
- 踩坑：stackCounts 单测首版断言自相矛盾（先断言 counts[1]==2 又断言其差 0.5）——交错分配后 index7 的小数直接并入叠1，应为 2.5。

### 测试

92 个单元测试全过。新增 CashStackLayoutTest 6 项（确定性/容量/交错映射/宽度边界/张数分配/封顶）；HomeSettlementTest 金币数映射 3 项替换为纸币计划 4 项。`:app:assembleDebug` 通过，待装机看效果（手感参数集中在 CashPile.kt 常量区：票面尺寸/叠高步距/抽出力度/错峰间隔）。

## 2026-10-07 · 首页金币视觉重绘与每次进入真实落币

### 设计复核结论

- 之前的扁椭圆金币无法被可靠识别为金币，且首次入场是整堆淡入、少量掉落仅作装饰；本轮将其视为未通过验收并重做。
- 评估了 OpenGL ES、Filament/SceneView 等真实 3D 路线。当前首页是固定视角的资源 HUD，真实 3D 会引入 `GLSurfaceView`/`AndroidView` 生命周期、渲染线程、模型/纹理、ABI 和低端设备维护成本；项目不新增 3D 依赖，采用 Canvas 2.5D。

### 本轮实现

- 单枚金币改为正圆币面：偏移暗金币身形成厚度，正面双层金属高光、内圈和中心 `¥` 标志；堆、HUD、小币、收入和入场粒子共用同一绘制函数。
- 增加独立 Compose Preview，固定展示大/中/小金币与堆体，先审查金币几何再复用到 Home。
- 每次 Home 真正进入或从后台恢复时，金币堆从 `pileCount=0` 开始；真实金币粒子从画布顶部落到目标槽位，落地后才增加堆数量，取消“整堆先出现、掉落只是装饰”的行为。
- 结算 session 仍只消费一次，后台恢复只重新展示当前真实资源堆，不重复播放相同收支 delta；普通重组不触发新的入场。
- 金币堆上限扩大到 24 个粒子槽位/更高容量布局；堆数量由剩余比例和月预算规模共同决定，对数规模因子满足小预算高剩余与大预算低比例仍可形成不同资源堆。

### 验证边界

- 本轮只运行 JVM 单测与 Kotlin 编译检查，不生成 APK，不执行真机操作；真机视觉验证由用户完成。


### 调整内容

- 重绘金币：增强暖金底形、内面层次、细内圈、高光与柔和投影；放大前景币并降低远景亮度，币形由 Canvas 几何直接绘制。
- 重构金币堆布局：在固定有限槽位内使用宽底窄顶、非网格抖动、深度缩放与轻微姿态变化；仍由预算剩余比例决定堆体，不按金额对应实际枚数。
- 收紧动画节奏：首次入场 5–12 枚前景金币快速落定；支出和收入各自驱动金额、已花与 pileCount 插值，合并发生时仍先支出后收入。
- 粒子槽位在协程取消时通过 `finally` 释放，Home session effect 退出时复位粒子，避免返回页面后残留或耗尽粒子池。
- 系统动画缩放和首页日期在生命周期恢复时刷新；数字区采用稳定高度，避免显示位数变化挤压操作按钮。
- 新增结算回退/负余额边界用例；账务真值及“会话开始即消费 snapshot”的展示边界不变。

## 2026-10-07 · 首页金币堆预算可视化系统（金币堆 + 结算动画状态机）

### 需求（用户详细设计稿）

Home 页升级为"极简游戏 Resource HUD"：金币**堆**代表剩余预算（替代上一版单币+圆环）；支出时金币从堆顶弹出碎裂、收入时金币从顶部掉落入池、金额数字随动画连续滚动；右上角"金币图标+¥96 今日可用"资源条；收支事件严格独立表现；设置提供动画开关。核心动画必须由真实金额/预算状态动态驱动（禁止固定 Lottie）。

### 关键实现（CoinPile.kt 374 行 + HomeScreen.kt 498 行重写）

1. **金币堆**：确定性布局预计算（固定种子、自底向上填充 42 枚槽位，金字塔形）——剩余比例→数量，数量天然决定宽度/高度，顶币按小数比例平滑长出。绘制全部 Canvas：底形/边缘环/内面/小高光/轻影，扁椭圆轻俯视透视，远处略小略淡、近处覆盖远处，堆零散抖动不成网格。
2. **动画状态机**：`Idle → PileEntrance → [ExpenseSettlement → IncomeSettlement] → FinalSettled`，按数据跳过空阶段；先支出后收入（间隔 200ms），收支绝不合并为净额（+100/−100 仍两个动画）。
3. **支出结算**：从堆顶被移除槽位弹出 2–16 枚金币（`moneyToVisualCoinCount` 分段映射封顶），抛物线上升（apex 由金额/预算比例调力度），最高点碎裂 3–4 金色碎片（继承水平方向+外扩+下坠+快速淡出）。
4. **收入结算**：金币从画布顶掉落（重力加速 easeInQuad），落定 squash+旋转回正，目标槽位=堆新增槽位，与堆数量动画同步交接（落定后 170ms 融入淡出避免与堆本体双重绘制）；堆已满时落顶部装饰位。
5. **数字滚动**：剩余/已花 Animatable<Float>（分）随阶段滚动，settle 后强制读真实值——动画中断/浮点误差都不可能错账。
6. **会话/生命周期**：`lastHomeSnapshot` 存 VM（presentation state）；`beginHomeSession` **消费即记录**（幂等）——旋转屏/重组/进程被杀均不重播不错账；跨月/预算修改/无快照→零 delta 会话（仅入场，不补播误导性巨变）；驻留期间数据变化（悬浮卡确认）由 settle 后的跟随协程平滑同步。
7. **性能**：粒子固定对象池（18 slot，参数 spawn 时写入，含 4 个碎片解析参数）；每帧只读 Animatable 进度在 draw phase 求值——动画期间零重组、零临时对象；`graphicsLayer` 只承担堆入场 scale/alpha（layer 级不重绘）；布局/调色板 remember 缓存。
8. **Reduced Motion**：系统动画时长缩放=0（ANIMATOR_DURATION_SCALE）或设置页"首页记账动画"关闭→堆 240ms reveal+数字快速到位+±¥ 横幅 1.6s，信息完整。

### 决策记录

- **预算口径升级**：剩余 = 月预算 + 当月收入 − 当月支出（收入动画要求收入能增大资源池；退款收入天然计入）。状态判定（Warning/Critical）仍按支出/预算比例——收入不掩盖预算消耗。金币堆比例 clamp 0..1（收入多时堆满、数字可超预算）。
- **事件边界"消费即记录"**：会话开始即推进快照而非动画完成后——动画中断最多损失动画本身，绝不重播或错账（动画不是 source of truth）。
- **Money→视觉金币数用分段阈值表**而非对数曲线：可预测、可单测（2–16 封顶）。
- 上一版"单币+消耗圆环"与 BudgetProgress 进度条删除——金币堆本身就是进度可视化。

### 测试

81 个单元测试全过（BudgetTest 适配收入维度+2 新用例；新增 HomeSettlementTest 10 用例：delta 独立性/跨月/预算修改/剩余口径/金币数映射单调性与封顶）。`:app:assembleDebug` 通过。

### 待真机走查

- 金币堆观感（42 枚容量/半径 11dp/行高 1.1R 的参数手感）、碎裂碎片数量与力度。
- 掉落/弹出时长（470–690ms）与 stagger（46–55ms）节奏。
- 快速记一笔→返回首页触发支出结算的实际观感。

## 2026-10-07 · 阶段四：UI 美化（设计 token 体系 + 预算首页 + 快速记账 + 全屏走查收敛）

### 设计方向（用户提供的设计稿，取代"仅打磨现有页"的保守路线）

**极简预算控制 App**："让用户首先看到自己还剩多少钱可以花"。首页 = 游戏 HUD 式预算视图（克制版，Financial App × Subtle Game Economy，不是 Finance Game）。核心决策：

1. **新增"月度预算"概念**（数据层从无到有）：自然月为周期，首页三层信息——剩余可用金额（最大视觉元素）→ 本月已花+消耗进度 → 今天建议最多花（剩余÷剩余天数含今天）。三态 Normal（金）/Warning（≥75%，琥珀）/Critical（超支，克制红）只靠颜色与简短文案表达，无情绪化语言。
2. **导航重构为 4 Tab**：首页/账单/统计/设置（≤4 约束）。快速记账主入口为首页大按钮（"记一笔"，金色），账单页保留小 FAB 兜底随手补录。
3. **新增快速记账页**（路由 `quickAdd`）：金额优先（¥0 大字 + 自绘 4×3 数字键盘）+ 分类 FlowRow；账户/日期/备注收进"更多细节"。目标动线：输入金额→选分类→记一笔。
4. **账单页不做游戏化**：成熟四段式（分类徽标/商户名称/分类·备注/金额），日期吸顶；编辑页=账单详情，金额升级为第一视觉主体。

### 关键实现

- **设计 token 体系**（`Theme.kt` 重写，10 行→180 行）：明暗两套暖色 colorScheme（暖白 F7F4EE/暖墨 1A1712 + 低饱和暖金 primary）；`AccBookColors` 语义扩展色（income/warning/critical/gold/goldDeep/hairline/8 色分类调色板）经 CompositionLocal 下发（`MaterialTheme.accBook`）；金额用 tnum 等宽字形（displayMedium/titleMedium/titleSmall）；Shapes 收敛（8/10/14/18/24dp）。
- **金币 Token**：Canvas 自绘（暖金圆币+双层描边细节+¥ 字形）+ 外圈预算消耗环形进度，扁平无渐变；金额变化 700ms 计数动画（余额被消耗的轻微游戏反馈）。
- **预算数据层**：`Budget.compute` 纯函数（6 单测）+ VM `monthlyBudgetCents`/`setMonthlyBudget`（SharedPreferences）+ `homeNetSpent`（**固定当前自然月**，不随流水页翻月）。
- **统计页**按"结论>趋势>分类细节"重构：一句化结论（支出·日均·最大项占比）+ Canvas 自绘每日支出柱状图（零花销日画发丝刻度）+ 分类占比条（与徽标同源取色）。
- **共享组件**（Components.kt）：`BudgetEditDialog`（首页/设置共用）、`CategoryBadge`（分类名首字+按名称哈希稳定取色，替代 emoji/图标依赖）、SummaryRow 精致化。
- **设置页**：新增"每月预算"入口（显示当前值/未设置说明）；`SettingRow` 支持 subtitle。

### 决策记录

- **首页消耗口径 = 当月支出合计 − 退款到账**（现金净流出，退款始终计入，不受"显示退款记录"开关影响）：预算关心"钱少了多少"，与账单页的账面口径（受开关控制）刻意不同。

## 2026-10-06 · 悬浮窗不弹的根因修复 + 捕获日志分通道 + USB 调试指南

### 用户反馈：支付页面出现但悬浮确认窗没有弹出

**根因（设计缺陷，已修）**：通知通道先入队时，页面捕获命中 ±1 分钟邻键条目 → 走"富化"路径后直接 return——**悬浮窗被富化路径抑制了**。只要通知监听正常工作，悬浮窗就永远不会弹，与验收标准"微信扫码付款 → 悬浮窗弹出"矛盾。修复：富化后照常弹出悬浮窗（支付瞬间给确认窗是正确的产品形态），**去重闸门移到入账时**——悬浮确认的 externalId 唯一索引兜底 + 确认/忽略时同时清理精确 dedupKey 与 ±1 分钟邻键的待确认条目（`deletePendingFor`），保证三通道仍只入账一次。

- `floating confirm disabled`——设置页开关关着
- `floating confirm skipped (no overlay permission)`——未授权"显示在其他应用上层"

- `floating confirm shown`——已尝试弹出（若仍看不到 → 支付保护中心/支付保险箱拦截，见保活页）

## 2026-10-06 · 阶段三：无障碍页面采集 + 悬浮确认窗 + 权限引导补全

### 实现内容（对照交接文档四项目标）

1. **无障碍服务骨架**：`AccBookAccessibilityService` + `res/xml/accessibility_service_config.xml`。事件只订阅 `TYPE_WINDOW_STATE_CHANGED|TYPE_WINDOW_CONTENT_CHANGED`、包名限定微信/支付宝、只读窗口内容、不申请手势能力（最小权限）。服务连接状态经 `CaptureCenter.a11yConnected` 状态流暴露给设置页/保活页；`isEnabled()` 读 `Settings.Secure.ENABLED_ACCESSIBILITY_SERVICES` 检测（保活页与设置页的"去开启"跳 `ACTION_ACCESSIBILITY_SETTINGS`）。
2. **页面识别规则**（`PageRules.kt`，风格对齐 NotificationRules，纯函数可单测）：输入=包名+页面文本快照（text/contentDescription 按控件树顺序，不依赖 viewId）。识别「支付成功页」（支付成功/付款成功/支付完成）与「账单详情页」（账单详情/交易详情），提取金额（标签行→独立 ¥ 节点→任意 ¥ 三层）、收款方/商家、支付方式、交易时间。
3. **悬浮确认窗**（`FloatingConfirmWindow.kt`）：`TYPE_APPLICATION_OVERLAY` + `NOT_FOCUSABLE|NOT_TOUCH_MODAL`；经典 View 实现（Compose 在 overlay 窗口需手工接 LifecycleOwner，不值得）；分类/账户用 ‹ › 循环选择（Spinner 弹层在无焦点窗口不可用）；确认直接入账并清同笔待确认；90 秒自动消失；忽略=删除同笔待确认条目。`SYSTEM_ALERT_WINDOW` 权限，设置页引导跳 `ACTION_MANAGE_OVERLAY_PERMISSION`。
4. **权限引导补全**：设置页加无障碍采集状态卡+开关、悬浮确认窗授权卡+开关；保活页加无障碍状态行 + **安卓 13+ 侧载"允许受限制的设置"通用第一步卡**（红色标题置顶）；分品牌补支付保护拦截对策（小米支付保险箱、荣耀支付保护中心、OPPO 系支付保护，华为已有）。

### 关键设计决策

- **跨通道去重改为 ±1 分钟容错**（`findRelatedPending`）：通知 postTime 与页面捕获时刻可能跨分钟，按原样精确匹配 dedupKey 会漏。通知先到→页面捕获命中邻近分钟条目→只回填收款方/支付方式（富化，不入新条目）；页面先到→通知捕获跳过。同一笔交易"通知+页面+悬浮确认"三通道最终只入账一次（悬浮确认 externalId 仍是 `NTF:`+dedupKey，撞唯一索引时提示"已入账"）。
- **dedupKey 分钟桶对齐交易时间**：页面有交易时间时用交易时间的分钟（与该笔支付通知的 postTime 分钟天然一致），无则用捕获时刻。
- **页面快照不落库噪音**：只有解析命中或含支付关键词（`looksInteresting`）的页面才进捕获日志，聊天/朋友圈浏览不刷爆 7 天/2000 条的日志表；debug 开关打开时全量落库用于采样。入队 note 只存"支付方式 X"等提取字段，**不存整页文本**（页面可能含卡号/余额）。
- **事件风暴四道闸**：config 限包名+事件类型（系统级）→ notificationTimeout=300ms → 400ms 防抖合并 → 页面文本指纹去重（同内容只解析一次，顺带挡"翻回同一笔账单"）。
- **跳过场景（宁漏勿错）**：退款页/收入页（"已存入零钱"、非"对方已收钱"的"已收钱"）暂不入队——通知通道与账单导入已覆盖退款与收入；超 24 小时的旧账单详情不入队（防翻旧账产生垃圾条目）。
- **状态行陷阱**："对方已收钱"是微信转账**支出**的状态、转账支出页也有"收款方"标签——方向判定里"对方已收钱"单独算支出，且"标签→值"提取带状态短语守卫，防止把"已收钱"当收款方。
- **Room v4→v5**：captured_notifications 加 `source` 列（NOTIFICATION/A11Y），defaultValue 与实体 `@ColumnInfo` 声明一致，迁移 SQL 与导出 schema 5.json 逐字核对过。

### 踩坑

- Kotlin 局部函数不能直接当值传递（`cyclerRow(..., dp, ...)` 报错），改 `val dp: (Int) -> Int = {...}`。
- `suspend` DAO 不能在非 suspend 函数里调用：`maybeShowFloatingConfirm` 被标记为 `suspend`（其调用点在协程内）。
- 无焦点窗口里 Spinner 弹层不可用 → 悬浮窗选择器用 ‹ › 步进；`NOT_FOCUSABLE` 同时保证无障碍的 `rootInActiveWindow` 仍指向支付页。

## 2026-10-06 · 通知规则引擎适配真实付款/退款通知（用户实测样本）

### 用户实测的四条样本与失败原因

| 通知原文 | 旧引擎结果 | 原因 |
|---|---|---|
| 微信 text=已支付¥12.80 | 未识别 | 支出关键词没有"已支付"，且金额是 ¥ 前缀（关键词后无数字） |
| 微信 text=[2条]微信支付: 退款到账通知 | 未识别 | 退款方向未处理（"退款到账"还会被"到账"误导向收款），且折叠汇总无金额 |
| 支付宝 text=你有一笔14.90元的支出… | 未识别 | **金额在关键词前面**（"14.90元的支出"），旧正则只找"关键词后的金额" |
| 支付宝 text=你收到一笔14.90元退款… | 未识别 | 同上 + 退款应打退款标记入账 |

### 修改

- **方向判定重构**：退款（退款/退回）优先于收/支判定——"退款到账"同时命中"到账"不能当普通收款；双向命中仍放弃。新增支出关键词：已支付、支付成功（注意不能加裸"支付"——微信收款通知里的"微信支付"会让收支双向命中）。
- **金额提取三层**：正向（关键词后跟数字）→ 反向（数字+元+关键词，覆盖"14.90元的支出/退款"）→ ¥ 金额兜底（已支付¥12.80 / 收款金额¥0.01）。
- **退款入账口径**：待确认队列表新增 refundMark 列（Room v3→v4 迁移；实体用 @ColumnInfo(defaultValue="NONE") 让新建库与迁移库 schema 逐字一致），确认入账时退款收入打 REFUND_INCOME——与账单导入口径一致，"显示退款记录"开关对捕获记录同样生效。
- **去重键升级**：加入方向与退款标记（pkg|INCOME|R|1490|分钟），同一分钟内同额的"支出+退款"不再互相吞掉。
- **折叠通知明细捕获**：监听服务补抓 InboxStyle 的 EXTRA_TEXT_LINES（与 EXTRA_MESSAGES 一并并入 text）——"[2条]"汇总的金额常在明细行里。
- 无金额的退款汇总通知：明确记日志"退款汇总通知常无金额，属预期，不入队"，等账单导入或后续无障碍通道兜底。

- **Room 唯一索引默认命名是 `index_表名_列名`，即使 UNIQUE 也没有 `_unique` 后缀**——迁移 SQL 必须与导出 schema 逐字比对（首版迁移就因索引名写错被 schema 校验逮住，真机升级会直接崩）。

- AGP 8 默认关闭 BuildConfig 生成，使用 `BuildConfig.DEBUG` 需 `buildFeatures { buildConfig = true }`。

## 2026-10-05 · 退款记录显示开关（"显示退款记录"）

### 需求

默认不显示退款（与原行为一致）；设置中开启"显示退款记录"后：退回的金额标记「退款收入」、被全额退款的支出标记「已退款」，计入总收支并额外显示「已取消收支」合计；关闭则不显示、不计入。

### 关键设计决策

- **退款记录始终入库、开关只控制显示与统计**（而不是解析时决定是否入库）：切换开关立即对全部历史导入生效，无需重新导入账单。数据库中多存的数据只是带标记的正常交易记录。
- **无需合成记录**：真实账单中微信退款本来就是成对的两行——退款到账行（收/支=收入、交易类型"XXX-退款"、状态"已全额退款"/"已退款(¥8.54)"）+ 原支出行；支付宝为"交易关闭"支出行 + "退款成功"不计收支行。解析时打标记即可。
- **部分退款的支出不打"已退款"标记**：微信原支出行状态"已退款(¥8.54)"（兼容"已退款¥8.54"）时保持普通支出（净支出本来就该是全额），退款额由独立收入行承载；支付宝部分退款原行状态仍"交易成功"，同理。
- **「已取消收支」= 退款到账金额合计**（收入侧）：全额退款时与已退款支出合计一致；部分退款时即为实际退回金额。
- 微信账单里"对方名-退款"是交易类型列的特征，交易对方列是干净商户名，分类猜测不受影响。

### 实现

- 数据层：`RefundMark` 枚举（NONE/REFUNDED_EXPENSE/REFUND_INCOME）新增到交易表；数据库 v1→v2 迁移（ALTER TABLE 加列，保留用户已导入数据）；所有月度查询（流水/收支汇总/分类占比/账户余额）加 `includeRefunds` 参数，余额查询把过滤条件放进 LEFT JOIN 的 ON 子句避免丢掉无交易账户；新增退款合计查询。
- 设置存储：SharedPreferences（"显示退款记录"布尔值），ViewModel 持有状态流，各查询流用 combine 联动开关。
- UI：设置页开关（含说明文案）；流水/统计页汇总行开启时显示第 4 列「已取消」；流水列表与导入预览的退款行显示「退款收入」/「已退款」角标；导入预览显示"退款相关 N 条"及当前开关状态提示。
- 「已取消收支」列不受开关外的其他过滤影响，仅由开关决定是否展示。

### 真实文件验证

- 微信 xlsx：**190 条全部入库**（原 157 条有效 + 33 条退款相关），中性交易仍跳过 2 条；dump 可见成对记录（姜胖胖：退款收入 50 元与原支出 50 元，时间一前一后）。
- 支付宝 CSV：**458 条入库**（444 普通 + 7 交易关闭 + 7 退款收入）+ 3 条不计收支跳过 = 官方总数 461 笔；Steam 两笔退款收入（34.80/24.48）正确识别。
- 25 个单元测试全部通过（更新微信旧版/新版 xlsx、支付宝 2026 用例覆盖全额/部分退款标记）。

### 踩坑

- 带过滤条件的 LEFT JOIN 若把条件放 WHERE，无交易的账户会因 NULL 比较被整体过滤掉，必须放在 ON 子句。
- 旧数据升级：Room 迁移列必须带 NOT NULL DEFAULT，且枚举列以字符串形式存储（Room 默认按枚举名转换）。

## 2026-10-05 · 适配 2026 版微信/支付宝真实账单格式（用户提供 docs/book 实测文件）

### 发现（真实导出与假设差异很大）

- **微信："用于个人对账"导出已从 CSV 改为 xlsx**：
  - 交易时间是 Excel 日期序列号（如 46299.627337962964），换算 = (序列号 − 25569) 天 + 小数部分×86400 秒；文件注明为 UTC+8 墙上时间，按本地时区转毫秒，与 CSV 路径语义一致；
  - 金额是无 ¥ 前缀的纯数字单元格；"不计收支"改称**"中性交易"**；
  - 表头列名不变，表头前同样有说明行。
- **支付宝 2026 版 CSV 表头大改**：
  - 列为：交易时间,交易分类,交易对方,对方账号,商品说明,收/支,金额,收/付款方式,交易状态,交易订单号,商家订单号,备注（旧版的 交易创建时间/付款时间/金额（元）/交易号 已不存在）；
  - 新增**"交易分类"列**（餐饮美食/日用百货/文化休闲…），可直接映射应用分类；
  - 交易订单号/商家订单号单元格带**尾部制表符**（trim 掉）；
  - 存在"交易关闭"的支出行，与其后"退款成功"的不计收支行成对出现，两者都跳过才不会重复；
  - 一笔可用组合支付方式（"中国银行储蓄卡(8920)&大牌补贴立减"）。

### 修改

- 新增 `XlsxReader`：正则解析 xlsx 的 sharedStrings 与第一个工作表（零依赖、可在 JVM 单测运行），支持共享字符串/内联字符串/数值单元格、缺失单元格补空、AA 以后的列号、XML 实体反转义。
- `BillParsers.parse` 按 zip 魔数(PK)嗅探 xlsx 与 CSV；`parseWechat` 时间兼容序列号；`parseAlipay` 按新表头重写、旧表头自动兼容（付款时间优先于创建时间仍保留）。
- `CategoryGuesser` 新增 `fromAlipayCategory`（官方交易分类→应用分类），未命中回退关键词猜测；餐饮关键词补充瑞幸/coffee。
- 跳过规则明确化：微信"含退款字样状态"跳过；支付宝"非成功/已到账状态"（如交易关闭）跳过；两者均只保留收/支=收入|支出的行。
- 界面文案更新导出格式说明（微信 xlsx / 支付宝 CSV）。
- 新增 `RealFileParseCheck` 手动核对工具：格式再变时把新导出文件放 docs/book，跑 `--tests "*RealFileParseCheck*"` 打印解析结果人工比对。

### 决策记录

- **金额一律用"分"（Long）存储**，避免浮点误差；`Money` 工具类统一解析与展示。
- **CSV 编码识别**：先 UTF-8 严格解码，失败回退 GBK；另外加了"含『交易』关键词"校验——GBK 字节序列偶发能被 UTF-8 解码成乱码而不报错，仅靠异常判断不可靠。
- **解析器用列名映射而非固定列位**：微信/支付宝改版调整列顺序时不至于直接失效。
- **退款行跳过**：微信"已全额退款"状态行、支付宝未完成（如等待付款）行不导入，避免净额重复；跳过数量在预览页明示。
- **UI 全部用 Material 3 默认样式**，按约定阶段一不做视觉打磨。
- **ViewModel 全局一个**（LedgerViewModel）：月份切换是流水/统计共享状态，且数据量级小，简单优先；后续阶段按需拆分。
