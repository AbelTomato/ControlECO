# 通知识别规则维护指南

> 目的：遇到识别不了（或不想再识别）的通知格式时，按本文档快速添加/修改/删除规则。
> 规则代码集中在一个文件：`app/src/main/java/com/accbook/app/capture/NotificationRules.kt`。

---

## 一、标准工作流（遇到新格式）

1. **抓样本**：确保设置 → 自动记账 →「记录所有应用的通知」开着（debug 构建默认开）→ 触发目标通知 → 设置 → 通知捕获日志 → 找到该条 → **点击复制原文**（含 pkg/title/text/bigText）。
   - 也可 Logcat 过滤 tag=`AccBook` 看 `onPosted pkg=... title=[...] text=[...] bigText=[...]` 一行。
2. **定位失败原因**：捕获日志/Logcat 里三类失败输出对应三个修复点：
   | 日志输出 | 含义 | 修复点 |
   |---|---|---|
   | `skip (not interested) pkg=...` | 包名不在白名单 | 加 `knownPackages` |
   | `rule ambiguous (both/none direction)` | 方向关键词没命中或同时命中收/支 | 调整方向关键词 |
   | `rule amount not found ...` | 方向对了但金额没提到 | 加/改正则 |
3. **改 `NotificationRules.kt`**（见下文修改点清单）。
4. **固化测试**：把样本原文加进 `app/src/test/java/com/accbook/app/capture/NotificationRulesTest.kt`（一条真实样本一个用例）。
5. **验证**：
   ```bash
   gradle :app:testDebugUnitTest --tests "*NotificationRulesTest*"
   gradle :app:assembleDebug
   ```
   装机复测，确认待确认队列出现预期条目。
6. **记录**：git 提交（样本原文写进提交信息），docs/开发日志.md 记一条。

> 及时性提醒：捕获日志只保留 7 天 / 2000 条，原始样本过时会自动清掉——写规则前先复制原文。

## 二、引擎机制（30 秒版）

`NotificationRules.parse(pkg, title, text, bigText, postTime)` 处理流程：

```
包名在 knownPackages？
  → body = text + bigText
  → 方向判定（优先级：退款 > 收入 > 支出；收/支同时命中 = 放弃）
  → 金额提取三层：正向正则 → 反向正则 → ¥ 金额兜底
  → 产出 ParsedNotification(type, amountCents, ruleName, dedupKey, isRefund)
  → CaptureCenter 写入待确认队列（dedupKey 撞车则跳过）
```

- **方向关键词**（当前）：
  - 退款：`退款 / 退回`（优先级最高，"退款到账"不会被"到账"带偏）
  - 收入：`收款 / 到账 / 入账 / 收入`
  - 支出：`已支付 / 支付成功 / 支出 / 消费 / 付款 / 扣款 / 支付凭证`
- **金额正则**（当前）：
  - 正向：`关键词后 0~8 个非数字字符 + 金额`，如 `收款0.01元`、`成功入账100.00元`
  - 反向：`金额 + 元 + 最多3个字 + 关键词`，如 `你有一笔14.90元的支出`、`你收到一笔14.90元退款`
  - 兜底：`¥12.80 / ￥12.80`（如微信「已支付¥12.80」）
- **dedupKey** = `包名|方向|R?|金额分|分钟` ——方向和退款标记必须在键里，否则同一分钟内"同额支出+退款"会互相吞掉。
- 金额只接受最多两位小数（`Money.parseCents` 限制），账单/通知里的金额都满足。

## 三、常见场景与改法

### 场景 A：已有 App 出了新通知写法（金额位置/写法变化）
1. 对照样本检查三层金额正则哪层没覆盖。
2. 优先把新关键词/写法**合并进现有正则**的交替分支（如 `(?:已支付|支付成功|支出|...)`），而不是另开一条规则。
3. ⚠️ 检查副作用：新关键词不能让**既有样本**的方向判定翻转。例：不能加裸词「支付」——微信收款通知里的「微信支付」会让收支双向命中而被放弃。

### 场景 B：新增支付/银行 App（新包名）
1. 捕获日志拿到确切包名（注意区分主包与推送子包）。
2. `knownPackages` 加包名；`sourceLabel` 加品牌显示名（显示在待确认列表和 ruleName 里）。
3. 先不动金额正则——通用三层（正向/反向/¥ 兜底）常能直接命中；跑测试确认，不中再按场景 A 补。
4. 银行 App 常见格式参考：`您尾号1234的账户于…入账100.00元`（正向）、`消费50.00元`（正向）。

### 场景 C：金额藏在折叠通知（"[2条]…"）
- 监听服务已把 InboxStyle 明细行（EXTRA_TEXT_LINES）和消息样式（EXTRA_MESSAGES）并入 text——先看捕获日志里该条的 text 是否已包含含金额的明细行。
- 若明细行有金额：正则按明细行文本写即可。
- 若仍无金额（如微信退款汇总）：**保持不识别**（无金额不入队是预期行为），靠支付宝式单条退款通知或账单导入兜底；日志会明确输出「退款汇总通知常无金额，属预期」。

### 场景 D：停止识别某类通知（删除）
按粒度从大到小：
1. **整个 App 不再捕获**：从 `knownPackages` 移除包名（原始日志也不再记录）。
2. **某类方向不识别**（如不想让"付款成功"类进队列）：从对应方向关键词（如 `expenseHit`）删掉该词。注意确认不破坏其他样本。
3. **某条规则只入日志不入队**：让它解析不到金额即可（如退款汇总无金额的现状）——不要用异常/硬 return 破坏流程。
4. 删除后：把对应测试用例改为断言 `null` 或删除用例，跑全量测试。

### 场景 E：金额/方向都识别对了，但想改显示
- 待确认列表里的来源与类型显示 = `ruleName`（规范：`品牌·收款/入账 | 品牌·支出/消费 | 品牌·退款`）+ `sourceLabel`；改 `sourceLabel()` 与 ruleName 拼接处。
- 默认入账账户推测在 `LedgerViewModel.guessAccountId`（包名 → 账户名关键词），新支付 App 在这里加映射。

## 四、修改点速查（NotificationRules.kt 内）

| 要改什么 | 位置 |
|---|---|
| 包名白名单 | `knownPackages` |
| 方向关键词 | `parse()` 里的 `refundHit / incomeHit / expenseHit` 三行 contains 列表 |
| 正向金额正则 | `incomeAmount / expenseAmount / refundAmount` |
| 反向金额正则 | `reversedAmount`（金额+元+关键词，覆盖"14.90元的支出"） |
| ¥ 兜底 | `currencyAmount`（一般不用动） |
| 显示名 | `sourceLabel()`、ruleName 拼接 |
| 去重键 | `dedupKey` 拼接行（改格式时注意方向/退款段必须保留） |
| 退款入账口径 | `isRefund` → CaptureCenter 写 `REFUND_INCOME`（勿动，与账单导入口径联动"显示退款记录"开关） |

配套文件（一般不动）：
- `capture/CaptureCenter.kt`：重发去重窗口、白名单外是否记录、待确认入队。
- `capture/NotificationCaptureService.kt`：文本抽取（title/text/bigText/明细行/消息样式）。
- 测试：`app/src/test/java/com/accbook/app/capture/NotificationRulesTest.kt`。

## 五、注意事项（踩坑记录）

1. **关键词改动的副作用**必须用全量既有测试回归（44+ 用例就是样本库）。
2. 方向歧义时引擎**主动放弃**（宁漏勿错），漏掉的会留在捕获日志——不要为了"抓到"放宽到双向命中仍入队。
3. 金额正则新分支要考虑小数与整数千分位：只可能遇到 `100` / `100.00` / `¥1,234.56` 三种（Money 已处理千分位逗号）。
4. 每条真实样本 = 一个测试用例，命名写清来源与格式特征（如 `alipay expense with amount before keyword`）。
5. 改动提交后同步更新 docs/开发日志.md：样本原文 + 失败原因 + 修改点，方便日后回溯。
